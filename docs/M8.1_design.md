## 5. Database read budget (O-81, Owner 2026-11-09)

On 2026-11-09 Turso blocked every read of the production and staging databases: the free plan's 500 million monthly rows read were used in eight days. Turso bills every row a statement scans. The nightly backup and the replay snapshot paged the price table with `LIMIT ? OFFSET ?`, so each page re-scanned every skipped row (about N²/(2·page) reads per pass, roughly 25 million per run at the recent window's size), and a full replay ran after every production deploy. The Owner took the Developer plan for November only; from December the build must fit the free plan.

- **D-903** Bulk reads page by key, never by OFFSET: the backup dump pages each table by `rowid` (rowid tables) or its primary key (WITHOUT ROWID tables), each page strictly after the last key of the one before, inside the same read transaction (one consistent snapshot, D-202 unchanged); the replay snapshot pages `price_bar` by `(code, d)` and `announcement` by `id` the same way. Each row is scanned about once per run. `tests/security/noOffsetPaging.test.ts` fails on any new `OFFSET ?` outside the short user-driven UI lists (news, reviews) and the one retention lookup.
- **D-904** Read budget (NFR, V2 spec ch. 10): the whole system (production; staging is off, D-906) stays under 20 % of the Turso free plan's monthly allowance, 100 million rows read and 2 million rows written a month, with the free plan's 500 million / 10 million as the hard ceiling. Estimated after D-903 and D-905: backup about 1–2 M reads a night, the light replay about 2–3 M a run, the intraday poll and scan about 5–6 M a month, everything else a few million; about 40–80 M a month in total. A delta backup (nightly changes, weekly full) is deferred: after D-903 a full dump costs about as many reads as the database has rows, and a delta adds restore-chain risk to the backup (a high-risk area) for a saving of a few percent of the budget. Build it when a full dump passes 2 M rows read a night (60 M a month).
- **D-905** The post-deploy full replay (D-195) runs only when the deploy changed what a replay depends on: the Worker dispatches it with `only_if_changed: "true"`, and `scripts/ci/replay-needed.mjs` compares the deploy with the approved deploy before it through GitHub's compare API. Strategy, arena, Cortex, replay, statistics, learning, money, config, backfill and calendar code, the replay scripts and the main-database migrations count; a UI, docs, workflow or test change skips the run. Anything unknown (no earlier deploy, a list GitHub cuts at 300 files, an API error) runs the replay, as before. A manual dispatch of mode `full` always runs.
- **D-906** Staging is off (Owner 2026-11-09: "Don't use any staging going forward on anything"): the `Nightly`, `Deploy staging` and `Staging E2E day` workflows are disabled in GitHub and the `praxis-app-staging` Vercel project is paused; the staging Worker cron was already empty. No release waits for a staging check (the staging E2E day before a release, D-860, is dropped); checks run on production only. The files stay so staging can come back on the Owner's word. The branches `main` and `release` stay in sync as before.
