## 2. Data model and rules

### 2.1 Windows, rows and determinism
- **Rows.** Every statistic in M6 is computed on **signal-ledger rows** (fixed notional A$600, ARN-080; D-088 mechanics) or on arena trades (execution comparisons). Excess e = net − mean of the row's 20 controls (D-078 #25); stress = P3 + 50 % slippage (ARN-083). Rows count only when their outcome is fully observed at the computation date (exit and all controls final; ARN-082 rule).
- **Lesson windows** (ARN-063, `lesson_split`): per lineage and split version, let Dev = the development entry sessions of `lineage_split` and P = its purge. Drop P sessions to place the purge between the parts: **L1 window** = the first ⌊⅔ × (|Dev| − P)⌋ entry sessions; **purge** = the next P sessions; **L2 window** = the rest of Dev. Frozen in `lesson_window` at split creation or roll (re-frozen at each roll, ch.15 l.43). Cross-family (market pool) lessons use, per boundary, the **earliest** split dates of the lineages involved (ARN-063). A deferred split (development < 252 sessions) has no L1/L2 window: only L0 lessons exist.
- **Number domains** as M4 2.1: money exact (bigint micro, rationals), statistics in float64 converted once at the statistics boundary, nearest-rank percentiles, fixed iteration order, SplitMix64 seeded by `deriveRngSeed(ARENA_MASTER_SEED, scope)` with new scopes `lesson:<lesson_id>:<split_v>`, `cmp:<comparison_id>:<week>`, `look:<finding_id>`, `gen:<lineage>:<week>`. No clock reads in engine code; `decided_at`-style instants are derived from D (D-078 #22).
- **Look-ahead** (TST-109, decision 38): every A6/A7 reader is bounded by D (rows with `entry_d` ≤ D and outcome observed by D's close, events by `cutoff(D)`), and the weekly run by its snapshot end. Validation and holdout rows are reachable only through the M4 `evaluateVal110` / `evaluateHoldout` entry points, which refuse without a `trial_ledger` row; the challenger generator and the lesson engine receive a `DevelopmentView` type that has no method returning non-development rows (module-boundary test, KB-040 "never shown to the agents that propose challengers").

### 2.2 Attribution (ARN-061; decision 25)
Per subject (arena `trade`, forward `ledger_row`, blocked signal) one canonical tag record:

| Tag | Source |
|---|---|
| family, execution, rule version, variant, tier | `signal`, `execution`, `cohort.rule_version` |
| signals/agents | contributing families (F6 classes), A2 event ids, A3 regime row, A4 pattern flags (informational) |
| regime | **entry-date** regime tag (`regime_daily.state` on the decision session; AGT-041 s11) |
| events | event group keys with category and polarity (rule-derived only, AGT-011a) |
| holding period | sessions from entry fill to exit fill (open: to D) |
| costs, slippage | brokerage in/out, modelled slippage in/out (micro, exact) from fills / ledger amounts |
| **MFE / MAE** | MFE = max over the holding sessions of (high_t − entry fill) ÷ entry fill; MAE = min of (low_t − entry fill) ÷ entry fill; raw highs/lows re-based by the exact split factors since entry (the D-088 rule); the entry session uses that session's high/low; ppm, rounded half-away; open subjects are recomputed nightly (new version row), final at exit |
| exit reason | IS / CS rule tag / TB-<id> / terminal / gap |
| filter decisions | ARN-011 filters and gates evaluated on the decision session (`signal.rules_json`, card `not_taken_reason`, `blocked` reasons from `runFamilies`) |
| blocked outcome | for a blocked or not-taken signal: the counterfactual fixed-notional row of the same family exits (the forward-ledger path, no capacity), `counterfactual_net_ppm`, final when that path ends |

Excess and stress for ledger subjects are copied from the ledger amounts; arena trades carry realised net P/L from fills (independent of the D-093 terminal-NAV basis, which stays an M4 known limit).

### 2.3 Lessons (ARN-063, KB-020, 06 l.117)
- **Template catalogue `LESSON_TEMPLATES_V1`** (versioned code table). Each template has an id, a scope (lineage or market), a subject selector over attribution tags, a metric (mean per-trade **excess** unless stated) and a statement template with slots {family, subject, metric, n, interval, grade}:

| Id | Subject (relevant rows) | Scope |
|---|---|---|
| LT-REGIME | family f, entry regime r | lineage f |
| LT-TIER | family f, tier t | lineage f |
| LT-EXIT | family f, exit kind (IS / CS / TB) | lineage f |
| LT-HOLD | family f, holding-period tercile (development terciles) | lineage f |
| LT-COST | family f, stress − P5 mean (cost drag) | lineage f |
| LT-FILTER | family f, blocked by filter k: counterfactual net (did the filter avoid losses?) | lineage f |
| LT-EVTECH | event families {F2, F3, F5} vs technical {F1, F4}: difference of mean excess | market |
| LT-CLASS | F6 with evidence class c present vs absent | lineage F6 |

- **L0 Observation**: a template cell on the L1 window with n ≥ `lesson_L0_min_n` (10, fixed, decision 42) and a point estimate; created by the learning run; no test.
- **L1 Hypothesis**: n ≥ `lesson_L1_min_n` (30) relevant rows in the L1 window **and** the two-sided 90 % interval of the mean metric excludes 0. Interval = 5th/95th percentiles of the replicate means of the ARN-081 circular block bootstrap (lineage's frozen block, B = max(1,000, 20 ÷ 0.10) = 1,000, scope `lesson:`), the same procedure as the M4 two-sided interval (decision 13). The lesson's **direction** s = sign of the point estimate. Fewer than 15 blocks → stays L0 with "insufficient independent blocks".
- **L2 Tested**: on the L2 window, n ≥ 30 relevant rows (else "L2 not reachable" with the date of the next roll that could add rows), studentised one-sided block-bootstrap test of s × mean > 0 (`studentisedTest`, scope `lesson:`), p ≤ α_j from the lesson's **α-investing pool** (2.4). Each lesson is tested at most **once per L2 window** (a re-test needs a new window after a roll). A non-rejection keeps L1 with "L2 test not passed (<window>)".
- **L3 Adopted**: an L2 lesson applied via Lane A (2.6) with all checks passing, or one referenced by a challenger that passed VAL-110 (`challenger.lesson_ids`). L0/L1 "unproven notes" never become L3.
- **Retired**: (a) the subject's rule version is retired, (b) at a roll the re-frozen L1 window no longer meets L1, or (c) the template version is withdrawn. Retirement is a new `lesson_grade` row; nothing is deleted (NFR-023).
- **Identity**: `L-<market>-<template>-<subject_sha8>-<rule_version>`; one lesson per (template, subject, rule version); grade history in `lesson_grade` (append-only), keyed by (lesson, seq). A recomputation at the same split version that would write the same grade writes nothing; a different value at the same split version raises (idempotent, ARN-102 style).
- **Never stronger than its grade** (KB-020): every rendered statement takes its verb from the grade (L0 "was observed", L1 "may", L2 "held in a later test", L3 "adopted"), a test checks every renderer path.

### 2.4 α-investing pools (ARN-063, `l2_alpha_investing`; decisions 14, 43)
- Pools: one per lineage (`<market>:<family>`) and one market pool (`<market>:*`) for cross-family lessons. Wealth starts at W₀ = 0.10 and is **never reset** (carried across rolls and windows).
- Test j: α_j = W/(2 + W). Outcome (Foster–Stine): rejection → W ← W + 0.05 (payout); non-rejection → W ← W − α_j/(1 − α_j) = W − W/2. Wealth never goes below 0; W = 0 → no further L2 tests ("α-wealth exhausted"). mFDR ≤ 0.10 by construction.
- Ledger `alpha_wealth` (pool, seq, lesson_id, window id, W_before, α_j, p, rejected, W_after): append-only; the next test reads the last row of its pool. Tests within one run are ordered by (pool, lesson id) so the sequence is deterministic. A test row is written **before** the lesson's grade row in the same transaction.

### 2.5 Comparisons (ARN-062, EML-037; decision 23)
- **Pairs list v1** (fixed): twins E(2k−1) vs E(2k) (live trades); each family vs its C2 (forward ledger excess); family vs family (forward ledger); tiers U1/U2/U3 within a family; filter taken vs blocked (counterfactual); cost profile P5 vs stress; event vs technical; regimes within a family.
- **Nightly (descriptive)**: per pair the difference of means with a two-sided 90 % interval from the ARN-081 block bootstrap over entry dates (block = the larger frozen block of the lineages involved; both sides resampled on the same blocks), labelled "descriptive — not a finding"; n < 30 per side → "not enough data (n = …)". Stored in `comparison_result` kind `nightly`.
- **Weekly (findings)**: Saturday's learning run tests every pair with ≥ 30 rows per side on forward data up to Friday: two-sided studentised bootstrap p, Benjamini–Hochberg at q = `comparisons_fdr_q` (0.10) across that week's tests. A BH discovery becomes a **candidate finding** with its direction and a look date = the first date its new data (rows entered after the detection date) holds ≥ 30 rows and ≥ max(75, 15 × block) sessions. **One confirmation look** on that new data, one-sided α = 0.05 in the detected direction: pass → **finding** (stated in sections 4–5 with its numbers), fail → discarded and the pair is **locked out for 60 sessions** (no detection). Pairs locked out or with an open candidate are not re-tested. Without a finding sections 4–5 say "no detectable difference (n = …)" (EML-037).

### 2.6 Lane A (ARN-064, KB-030…032, decisions 11, 12, 22)
- **Targets in M6**: (a) agent playbooks `knowledge/{market}/agent-playbooks/{agent}.md` for the LLM agents A1 (R1), A2/A3 (R2), A6/A7 (R3), A8 (R5); (b) Owner-facing notes (lesson documents, review section 4). Alert-routing materiality adjustments are not produced in M6 (no template targets them). Watch-lists, filters, thesis-breakers, rule parameters and anything a trade reads are **never** Lane-A targets (KB-030; test).
- **Eligibility** (automatic): an L1 lesson whose six Critic checks pass (5 may be "pending" for L1, 2.7) → "Unproven notes"; an L2 lesson whose six checks pass → "Guidance" and its grade becomes L3. L0 lessons are not applied automatically. The Owner may force-apply a lesson whose check failed: it appears under "Unproven notes" with "forced by Owner", keeps its grade, never becomes L3, audit-logged (decision 22).
- **Assembly** (KB-032): playbook text is built **only** from structured fields (statement template, metric, n, grade) by `renderPlaybook(agent, lessons)`; no LLM prose in M6; order Guidance then Unproven notes, each by grade desc, then |estimate| ÷ se desc, then lesson id; truncated at `playbook_max_tokens` (1,500, `estimateTokens`), dropped lessons listed in the change ledger. Deterministic injection checks on the rendered text: phrases of `llm_injection_phrases`, imperative patterns, URLs, and any code or number absent from the lesson record → the lesson is excluded and the event logged (KB-061). Third-party text never enters (structurally: the renderer has no announcement input).
- **Change ledger**: one row per changed playbook (before sha → after sha, unified diff stored, lesson ids added/removed, effective date = next session, actor `A6`), and a new `playbook_version`; listed in review section 4. Unchanged text writes nothing.
- **KB version** (LLM-031, decision 46): `kb_version` = `kb-<n>` where n is the id of the latest `change_ledger` row that changes LLM context (playbook, lesson grade, rule version, Owner notes); every router gets it from `currentKbVersion(db)` at start of a run; a change makes all cached answers miss (the `llm_cache` key already contains it).

### 2.7 Critic checks (AGT-041/042; decisions 15, 16, 17)
| # | Challenger (rows = the VAL-110 (i) rows of the same access) | Lesson ≥ L1 (development rows only) |
|---|---|---|
| 1 sample size | ≥ 100 rows and ≥ 15 blocks on validation (ARN-082 minimum); effective N reported | n ≥ 30 relevant rows and ≥ 15 blocks in the window of its grade |
| 2 regime | per entry-date regime with ≥ 30 rows: point estimate of excess; **fail** if negative in at least half of those regimes; one qualifying regime counts (negative there = fail); none → "not assessable", shown, not a failure | same, in the lesson's direction s (fail if s × estimate < 0 in ≥ half) |
| 3 stress costs | VAL-110 (iv): stress point estimate > 0 | positive-direction lesson: mean absolute net under P3 + 50 % slippage > 0 on its rows; negative-direction lesson (an "avoid" lesson): the stress excess keeps the claimed sign |
| 4 data issues | share of rows with a quality flag (quality-suspect, stale-data, first-seen difference, survivorship-exposed for event families) ≤ `survivorship_flag_share` (5 %), survivorship qualifier from M4, and the input-bound audit (all rows entered in the tested window with outcomes observed before the test date) | same flags on its rows, same 5 % share, same input-bound audit on its window |
| 5 luck | VAL-110 (i) | the ARN-063 L2 test: pass if L2; **pending** (not a failure) while "L2 not reachable" or not yet run; **fail** if the L2 test ran and did not reject |
| 6 bounds | every parameter of the version within its ch.15 bounds (KB-010) | n/a (pass) unless the lesson names a parameter, then its value within bounds |

Checks are computed where the rows are (lesson checks in the learning run, challenger checks inside the evidence run on the same access, no extra trial), stored in `critique` with every number and state, and re-read nightly. A failed check blocks Lane A (lesson) or promotion (challenger) (AGT-042). Worded concerns and alternative explanations are R3 text in `critique_note` (never blocking, shown in-app and counted in section 4).

### 2.8 Rule versions and challengers (KB-010…012, KB-040…043, ARN-065, ARN-085; decisions 17–22, 32)
- **`rule_version`**: id `<family>.v<n>` (M4 already uses `F1.v1`…), market, parent, `origin` seed / challenger / owner / rollback / force, `params_json` = the **full** canonical set of that family's §15.3 B keys (plus F6 / insider / polarity B keys), `params_sha`, `spec_json` = the family's declarative description (rule-schema v1: conditions {field, operator, value-or-param-ref}, AND groups, `count_of`, actions enter/exit/size/gate; generated from the interpreter's rule table and validated: unknown fields or operators rejected, every param-ref within its bounds), `registered_d`. v1 per family and market is **seeded** idempotently from the current registry values (grade L0, label UNVALIDATED, metrics empty; KB-012). Versions are immutable (KB-011).
- **Parameters are the only degree of freedom** in M6 (decision 32): a challenger changes ≥ 1 B-key value within bounds; a structural change is a new lineage (FAM-101). After seeding, B keys are no longer edited in the configuration editor: an Owner edit creates an `owner`-origin version that enters Lane B (KB-050, decision 45).
- **Live parameters** come from `rule_version.params_json` (the cohort's `rule_version`, ARN-102), no longer from config. Batch 2b evaluates `runFamilies` once per **distinct active version** of a family (incumbent of live cohorts, versions still held by shadow cohorts, challengers in `shakedown`/`review`/`approved`) on the same day inputs; only versions held by a live cohort create orders; every version's candidates are stored for the forward ledger (`fwd:<market>` / `cand:<d>`, D-093), so challengers accumulate unfunded forward rows (decision 44).
- **Lifecycle** (KB-040, `challenger.state` one-way; every transition an append-only `challenger_event`):

| State | Entry rule | Exit |
|---|---|---|
| `proposed` | generator or Owner version; `trial_ledger` row kind `challenger` written at creation (ARN-085); hypothesis document | first learning run with enough validation entries → `replay` |
| `replay` | development replay of the version (ledger + controls) | evidence: `validation_access` row first, VAL-110 (i)–(vi) incl. (ii) vs the incumbent over the same period, Critic 2 on the same rows; **pass → `shakedown`; any failed component → `rejected`** (slot stays used, not re-tested); "insufficient" → stays, reachable date shown, **no access charged** (entry-count pre-check, decision 47) |
| `shakedown` | candidates evaluated nightly on the live feed, unfunded | after `shakedown_sessions` (10) trading sessions whose 2b and 3 succeeded with no rule-load or ledger error → `review`; an operational error resets the count (not evidence) |
| `review` | Critic checks 1–6 read (1–5 stored by the evidence run, 4 re-checked on current flags, 6 re-checked) | all pass → marked `ready`, waits for the Owner's approval → `approved`; any fail → stays in `review` (the Owner may force-apply or reject) |
| `approved` | Owner approval (ROL-102; audit-first) | `promoted` at the twins' next common restart boundary (2.9) while ≤ 3 promotions in that week; else waits |
| `promoted` / `rejected` / `retired` | terminal | — |

- **Limits**: ≤ `max_challengers` (8) challengers per market in states proposed…approved (the generator and the Owner route refuse beyond it); ≤ `max_promotions_per_week` (3) **applied** promotions per Melbourne ISO week per market; a lineage whose trial budget is exhausted gets no new challenger until its next roll (ARN-085); a family with an `arena_control` `killed` row is **frozen**: no generation and no promotion (KB-043; Owner rollback/force-apply still allowed with a second confirmation, decision 19).
- **Generator** (decision 20, weekly, deterministic, development only): for each lineage with budget and a free slot, at most one challenger per week: candidate steps = each B key of the family moved one grid step (key step from the registry, else 10 % of its range) up or down within bounds, prioritised by keys named in that lineage's L2/L3 lessons (`param_hint` of the template); each candidate's development ledger is replayed (development only, no trial); the best development mean excess with ≥ 100 rows and ≥ 15 blocks wins; ties → key name, then direction. The winner becomes `proposed` with `lesson_ids`, its trial row and a hypothesis document (template; optional R3 wording, decision 20). The LLM never proposes a value.

### 2.9 Promotion, force-apply, rollback and the holdout roll (ARN-065, ARN-082, KB-043, KB-050, AGT-042; decisions 18, 19, 22)
- **Boundary**: the restart group `TW-Fk` (E(2k−1), E(2k), C2-Fk, C3-Fk) restarts together (ARN-053, D-076), so "the target execution's next cohort boundary" (KB-040) and "both twins at their next common cohort boundary" (ARN-065) are the same session in this build. `cohortWriter`'s group restart, inside its existing transaction, reads the pending `promotion` row of the family: successors of the two E executions start with the new `rule_version` and its `params_json`, `execution.rule_version` is updated (the only allowed change), the promotion row goes `pending → applied` with `applied_d`, and a `change_ledger` row is written. Ending and shadow cohorts keep their version (ARN-065 s11). Controls are unaffected (they map the matched signal's exits).
- **Holdout roll at promotion** (ARN-082): a new `lineage_split` version (reason `roll`) by a new pure `rollLineageSplit`: holdout = entries after max(registered_d, promotion d) + one purge (usable once holdout-length + completion window has passed), validation = the validation-length window ending one purge before the new holdout, development = everything earlier; block and window lengths re-measured; `lesson_window` re-frozen; trial budget rolled (`rolledBudgetAtRoll`, D-078 #26). The promoted version shows "validation passed — holdout pending (<date>)" until the learning run's holdout confirmation (one `holdout_access`, α = 0.05 ÷ L) gives PASSED-BACKTEST or not (ARN-086).
- **Force-apply** (Owner, challenger in `review` or an Owner version): applied at the next boundary like a promotion but **not a promotion**: no cap count, no roll, label resets to UNVALIDATED with qualifier "forced by Owner" (AGT-042, KB-050).
- **Rollback** (Owner): a new version (`origin rollback`, parent = current head, `params_json` copied from the chosen earlier version) applied at the next boundary; no VAL-110, no cap count, no roll; label UNVALIDATED with "rollback of <v>"; history never rewritten (KB-043, ARN-067).
- **Retire** (ARN-092): a version FAILED at a forward look or dominated is set `retired` by the learning run (challengers) or proposed to the Owner (live version: needs a rollback or a promotion to replace it; never left without a version).

### 2.10 KB documents (KB-001…003, EML-015; decisions 29–31, 33)

### 4.2 A6 nightly `learn` stage (ARN-060…069; inside the 10-minute nightly budget, learning loop ≤ 5 min, NFR-011)
1. **Attribution**: new/updated `attribution` versions for trades, forward rows and blocked signals of D (2.2); final rows never change.
2. **Comparisons**: nightly descriptive rows (2.5).
3. **Lesson staging**: read lesson grades written by the last learning run (no new statistics nightly; development data are static between rolls); list "new or changed since the last review" for section 4.
4. **Critic gate**: read the latest `critique` per lesson ≥ L1 and per challenger in `review`; re-check 4 (current flags) and 6 (bounds) for challengers; write a new `critique` row only when a state changes.
5. **Lane A** (2.6): recompute every agent playbook; changed text → `playbook_version` + `change_ledger` (effective D+1); L2 → L3 grade rows for newly applied lessons.
6. **Challengers**: shakedown session counting (from D's 2b/3 status and the version's candidate rows), `shakedown → review` transitions and the `ready` mark of challengers in `review`; nothing promotes here (promotions happen in 2a's restart step).
7. **Plan** (ARN-066): candidates in fixed priority — (1) Lane-A changes effective tomorrow, (2) challenger steps due (review, awaiting Owner approval, promotion at the next boundary, holdout pending), (3) lessons whose L2 test becomes reachable, (4) open data weaknesses (quality flags, coverage < 90 %, sources off), (5) open candidate findings with their look date; each item carries reason, lesson id (or `no-lesson:<kind>`), lane and a success measure {metric, threshold, check date}; the first 5 by (priority, id). Yesterday's items get a `plan_review` row (measure evaluated when due, else `not_yet_due`).
8. **Documents**: render the documents of every record written on D (2.10); new `document` versions.
9. **KB version**: if any context-changing `change_ledger` row was written, the `words` phase and tomorrow's routers use the new `kb_version`.
10. Run record counts; `degraded` if a sub-step was partial; a failure in one sub-step never stops the others (AGT-004).

Non-trading days (DAT-022, decision 3): `learn` runs a reduced variant inside the reduced pipeline (no attribution or comparisons; plan review, documents incl. the non-trading review of the previous day, Lane A unchanged) so section 4 of a non-trading review has A6 content; challengers count only trading sessions.
