# What runs where: CI, local and scheduled gates

V1-I15, D-796; rewritten for the recorded day in M18 (OPS-107, D-964, D-965). One page so nobody assumes "green locally" or "green on the PR" means more than it does. Job names are those of `.github/workflows/ci.yml`. There is **no staging environment** (D-964): what staging used to prove is proven in CI by the `recorded-day` job, by the CI streak and by an authenticated ZAP scan of the local build.

## Known asymmetries

- **Local green is not CI green.** The Linux jobs, the gitleaks history scan, the strict fixtures step and the e2e production build do not run in a plain `npm test`. After a push, read `gh run list` for the branch (all jobs), not only the local gate.
- **Timing-sensitive tests.** About 30 test files use fake timers or `Date.now`. `tests/quarantine.json` is empty today; a flaky test goes in that record with an expiry (TST-131) rather than being retried.
- **Timing assertions (R3-I4, D-820).** Three places assert a measured time or CPU budget and run in the required `app` and `worker` jobs: the Worker CPU budget (`worker/test/m5Slots.test.ts`, PLT-070: median under 5 ms and 8 ms against 10 ms), the default-size cohort replay under 60 s (`tests/replay/cohortReplay.test.ts`) and the quarterly live look (`tests/cortex/look.test.ts`, bounded by the 30 s test timeout). Their names start with `[timing]`. Locally they run once with no retry; in CI only (`CI=true`, set by GitHub Actions) each gets **one** retry, so one noisy shared runner does not turn the release gate red while a real slowdown, which fails twice, still does. The budgets and margins are unchanged and the measured median or seconds is logged on every run (`[timing] ...` lines in the job log), so a creeping trend stays visible. A test that needs more than one retry goes in `tests/quarantine.json`, not in a higher retry count. Find them all with `grep -rn "[timing]" tests worker/test`.
- **Release gate list.** `CI_REQUIRED_JOBS` in `scripts/ci/release-gate-core.mjs` now equals the `needs` list of the `release-gate` job (all nine jobs, including `audit`, `coverage` and `checks`; `recorded-day` is waited for through `needs` and judged by its own condition); `scripts/ci/ci.workflow.test.mjs` fails if the two drift apart (D-796).
- **Real-key evidence is Owner-run.** The real-key restore drill is dispatched by hand (`restore-drill.yml`); the release gate only reads that it happened and how recently. The staging end-to-end day, the staging ZAP scan and the Nightly suite are retired: `staging-e2e-day.yml`, `zap-baseline.yml` (staging job removed), `nightly.yml` and `deploy-staging.yml` are dispatch-only and kept for history and the rollback runbook.
- **No waivers (D-964).** `docs/release/waivers.json` keeps its file shape with an empty list: `WAIVABLE` in `release-gate-core.mjs` is empty, so no condition can be waived and any entry is ignored (the summary says so). The D-860 machinery (at most 14 days, Owner only, shown as WAIVED, never PASS) stays in the code, dormant, for a future decision that re-opens a condition.
- **Recorded-day host guard (D-965, NFR-040).** Every process of the recorded day runs with `PRAXIS_ENV=recorded`: `src/lib/data/recorded/hostGuard.mjs` refuses every host except loopback, in `fetch` and in every TCP connect, counts refusals in `$PRAXIS_NET_LOG` and writes one marker per process. The job's last step ("Network assertion ...") fails on any refusal or on a process that wrote no marker. The Next.js app installs the guard (and a simulated clock, and in-process synthetic quotes) from `src/instrumentation.ts` only when `PRAXIS_ENV=recorded`. Chromium (the viewer walk) is a separate process and is not covered by the marker; it only visits loopback.
- **The profile rule (M19, MKT-107, AT-67, D-1000, D-1075 to D-1078).** A fact about a market (its code, exchange, zone, session and cut-off times, currency, Yahoo suffix, index, parcel and tick literals) is written once, in the profile seed (`src/lib/market/seed/**`) and the few rule tables that are keyed by market (`src/lib/market/**`, the files in `seed/allow.mjs`). Everything else reads the profile (`profileOf`, `homeProfile()`, `HOME_*`, `OWNER_TZ`). `node scripts/ci/market-literals.mjs` fails on a literal outside that list; `--count` prints the D-991 count (files that hold a quoted `AU`; 0). The Owner's zone (Australia/Melbourne), its date locale (en-AU) and the word "Melbourne" are not market facts and are not scanned. A new exception is an entry in `EXTRA_ALLOW` of the script, with a reason; an entry that matches nothing fails the scan. Tests, `e2e/` and fixtures are not scanned.
- **Off in production (M19, MKT-110, AT-68).** The three proofs run on every push, not only on release: the Worker and the scripts refuse a market that is not enabled (`worker/test/at68Worker.test.ts`, `tests/acceptance/v3/at68.test.ts`), a write for it is refused by a database trigger and raises an incident, and no page shows it to an Editor or a Viewer (`e2e/market-off.spec.ts`, empty lane, never with `PRAXIS_MARKETS_ENABLED` set). The `recorded-day` job ends (before its network assertion) with the production-shape check on its own database: AU enabled and `full`, IN and US built, disabled and `off`, no counted row for a market that is not enabled, and a slot build that names AU only. A development lane may set `PRAXIS_MARKETS_ENABLED=AU,IN,US` (`e2e/seed/states/markets-dev.mjs`); a CI lane may not (`scripts/ci/e2e-listing.test.mjs` checks).
- **The development-mode days (M20, D-1119, D-1198).** `recorded-day-dev` is a separate job so the production-shape `recorded-day` job is untouched. `PRAXIS_MARKETS_ENABLED=AU,<CODE>` is set on its one data-only step and nowhere else in `ci.yml`, in no package script and in no Playwright config (`scripts/ci/e2e-listing.test.mjs`, `scripts/ci/ci.workflow.test.mjs`); `e2e/market-off.spec.ts` and `assert-production-shape.mjs` still prove the production shape. With no recorded session the job warns and succeeds, so a green `recorded-day-dev` with the warning is not evidence for the market: read the step list for the data-only step. The kill, the switch and the projection are code only (AT-71); the Owner performs the switch after the merge.
- **Review checklist: keyset paging (D-959).** Every keyset `ORDER BY` needs a named index, and `OFFSET` has no exception (`tests/security/noOffsetPaging.test.ts`).
- **Merged-tree security tests (D-978 item 4).** `tests/security/*` run inside the `app` and `recorded-day` jobs on the merged tree by construction (CI runs on the head commit), so no separate run is needed.
