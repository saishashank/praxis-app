## 2. Data model and rules

### 2.1 Time (DST-safe, D-059/D-060)
- Every M5 local time (08:00, 09:54/09:58, 20:00…20:45, 20:40, 21:50) runs on the Worker clock: `sydneyLocal()` minute arithmetic (no Intl, D-060), slot claims `slot:<id>:<local date>[:<n>]` in `worker_state`. Melbourne and Sydney share offset and DST dates (`worker/src/schedule.ts` header). No M5 time falls in the 02:00–03:00 DST gap/overlap; the D-059 rule (gap → forward, overlap → first instant) still applies to any configured time.
- "Local date" of a review/brief/reminder = Melbourne calendar date of the scheduled local minute, never of the wall clock at finish (PLT-019 spirit). A send that finishes after midnight keeps its date.
- YAML watchdog (only if its schedule is enabled later): generated dual UTC triggers `40 9`, `40 10`, `50 10`, `50 11` (20:40/21:50 in AEDT and AEST); the first step maps `github.event.schedule` + the current Melbourne offset to `2040`/`2150` or exits 0 (PLT-019); a `workflow_dispatch` input `slot` replaces it for Worker or manual runs. Lines are produced by `scripts/time/genWatchdogCron.mjs` and a test compares them with the YAML (OPS-102).
- Vercel Cron heartbeats stay at 00:20 and 11:10 UTC (D-066): 10:20/21:10 AEST, 11:20/22:10 AEDT — both after 20:45 local in both seasons.
- Instants are ISO-8601 UTC ms text; dates are Melbourne `YYYY-MM-DD`; email bodies print Melbourne local time with the zone abbreviation (EML-022).

### 2.2 Materiality, membership and tiers (AGT-011, AGT-014, AGT-015, AGT-115)
- **Tracked** = U1–U3 of the latest `universe_snapshot` ∪ held. **Held** = an open trade of a *live* cohort of E01–E12 in an active-or-full market (controls C1/C2/C3 and shadow cohorts never count). **Watch-list** = codes with a `signal` row (taken or not) in the last `watch_list_window` (20) sessions ∪ unexpired `watch_list_owner` rows. **Candidate** = watch-list ∪ codes with a pending entry order (decision 43).
- Rule materiality (`MATERIALITY_RULES_V1`, versioned table in code; ASX `type` code first, then word-bounded title patterns, as `EVENT_RULES_V1`): 3 = price-sensitive or halt/suspension/exchange query on a held code, or takeover/scheme on a tracked code; 2 = price-sensitive on a watch-list/candidate code, results, guidance change, capital raising, director on-market trade (Appendix 3Y) on a tracked code; 1 = other announcement on a tracked code; 0 = otherwise. `materiality_llm` (R1, ±1) is stored separately and used only for in-app wording and P1/P2 ordering, never for tiers that change email (AGT-011a; decision 21).
- **Weight** = market value of the held position at the latest close (raw close × qty, micro) ÷ that execution's latest NAV (micro), compared exactly as a rational with `alert_p0_weight` (10 %). One alert per (item, execution) holding the code; the alert's tier is the highest across executions.
- Tier: **P0** = (held, weight ≥ 10 %, materiality 3) or halt/suspension of a held code (ASX type or title; the DAT-127 proxy is P1, decision 27); **P1** = held below 10 % with materiality ≥ 2, or watch-list with materiality 3, or pre-open re-check failure (ARN-020a s13), or a regime transition (UXN-251), or a red thesis-breaker on a held position that is not P0; **P2** = everything else with materiality ≥ 1 (materiality 0 items create no alert row).
- Alert key (idempotent): `ann:<market>:<source>:<ann_id>`, `tb:<trade_id>:<breaker>:<d>`, `regime:<market>:<d>`, `preopen:<market>:<d>`, `proxy:<market>:<code>:<d>`. Writers use `INSERT … ON CONFLICT DO NOTHING`; a duplicate is never re-emailed.

### 2.3 Email budget arithmetic (EML-004, EML-020, EML-023, NFR-006 l.21)
- Per Melbourne date and environment: `email_daily_cap` 20 = 3 **reserved** (`review`: the Evening Review or its minimal fallback, same key; `incident`: the first new S1/S2 incident email of the day; `reminder`: EML-023) + 17 **pool**. P0 alerts take pool slots and at most `p0_email_daily_cap` (10) of them; P0 never uses a reserved slot (NFR-006 l.21). A second and later incident email, tokens-due, unread-7-days, Morning Brief and test emails use the pool.
- Monthly: `email_monthly_cap` 300 per Melbourne calendar month; once reached, only reserved-slot kinds and S1 incidents send (decision 25).
- Counting = rows of `email_message` with status in (`claimed`, `sent`, `failed` after an accepted attempt) for that date/month; suppressed rows (`suppressed_cap`) are listed in the next review's section 9 (EML-004). The count and the claim happen in one statement (conditional insert with a sub-select), so two racing senders cannot both take the last slot.
- Staging: own counters (separate database), every subject prefixed "[STAGING]", and the provider is the mock except one live "[STAGING]" email per test run when `EMAIL_LIVE=1` is set for that run (EML-004, NFR-040).

### 2.4 Email keys and idempotency (EML-010, REQ #12)
- One `email_message` row per **email key**: `review:<d>` (Evening Review, minimal review and watchdog fallback share it), `p0:<alert_key>`, `p0b:<first_alert_key>` (batch), `inc:<incident_id>:open|s1`, `tokens:<d>`, `unread7:<d>`, `reminder:<d>`, `brief:<d>`, `test:<n>`, `dbdown:<d>:<slot>`.
- Send protocol: (1) claim = conditional insert of the key with status `claimed` (fails → someone else owns it: stop); (2) render; (3) provider call with header `Idempotency-Key: <env>:<key>` [VERIFY Resend support and 24 h window]; (4) record the attempt and move the row one way (`claimed → sent | failed | suppressed_*`). A `claimed` row older than `CLAIM_STALE` (3 min, as the Worker clock) with < 3 attempts may be re-claimed by a later invocation (attempt n+1) with the same idempotency key, so a crash after acceptance cannot produce a second email inside the provider window.
- The review content is frozen in `evening_review` before the claim; the minimal fallback writes its own version row but the same email key.

### 2.5 Thesis-breaker evaluation (AGT-111, D-089 catalogue)
- Inputs: the card's breaker list (`card_json.thesis_breakers`: id, check, trigger, amber level stored at card time per D-089) and data bounded like `DecisionView` (bars ≤ D, items with `published_at` ≤ evaluation instant).
- Status per breaker: **red** if the condition holds; **amber** if (continuous breakers TB-EVLOW, TB-SI, TB-SMA) the monitored value is at or beyond the card's amber level, or (TB-KW) a keyword match is awaiting confirmation; else **green**. Event breakers TB-NEG/HALT/RAISE/REGIME are green/red only. Position status = worst breaker (decision 15).
- TB-KW: keyword title match → amber `awaiting_confirmation`; confirmed **red** when the same announcement's A2 `event` row (rule table) or its ASX type code is guidance-down, withdrawn or halt in the next nightly cycle; otherwise back to green with reason `unconfirmed` after `tb_kw_confirm_sessions` (1) (decision 16).
- Effects: nightly red on a held position → batch 2b creates an `exit_cs` (rule `TB-<id>`) for the next open (AGT-111 s11), plus an alert; red on a pending buy at the pre-open re-check → cancel (ARN-020a); intraday Sentinel hits on held codes → evaluation row (phase `intraday`) and alert only (AGT-012: the Sentinel never changes orders).

New runner kind `route`: a signed POST (WORKER_HMAC_SECRET, nonce, `redirect: manual`, `AbortSignal.timeout`, as `universe.ts`) with the slot claim of the clock; at most 3 attempts per slot occurrence, then an in-app notice (PLT-012). Every route slot is market-independent except `pre-open` (market-bound). The kill switch `dispatch_enabled` gates route slots too. Idle-minute rule of `clock.ts` is kept: no DB request unless a slot window is open (alert-flush adds one read every 2 min in its window ≈ 420 reads/day).

### 4.2 A1 Sentinel cycle (AGT-010, PLT-012/070/075, DAT-122/123)
1. Worker (existing `runAsx`): on a due even minute and every switch on, conditional GET through the rate token. New: on 200, compute SHA-256 of the body (`crypto.subtle`, I/O-like, not CPU-heavy); if the body ≤ `sentinel_body_max_kb` (256) and its hash ≠ the stored last hash, POST it signed to `sentinel-ingest` (one subrequest). Outcome counters go into `sentinel_poll_day` in the same batched write as the token outcome (PLT-075). 304 counts `not_modified` (a successful poll).
2. Route (`src/lib/sentinel/ingest.ts`, Node, `maxDuration` within Hobby [VERIFY]): verify HMAC + nonce; parse the feed (parser `asxFeedV1`, format `TODO(fixtures)` until a recording exists, D-058); insert all new announcements (`ON CONFLICT DO NOTHING`, first-seen); select up to `sentinel_max_items_per_run` (40) unassessed announcements by `published_at` (the rest are carried: the `announcement` table **is** the queue); assess (2.2), write assessments, alerts and intraday thesis-breaker rows in **one** batch; then send the P0 emails (4.3). Response `{new, assessed, carried}`; the Worker re-posts nothing — carried items are picked up by the next call or by `alert-flush` (which also assesses up to 40 carried items).
3. Timeout/error: the Worker records attempt n in `worker_state` `si:<body_sha>` and re-posts the same body on the next poll tick even if unchanged; after 3 attempts an in-app notice (incident S3 `sentinel_ingest_failed`) and the body is dropped (items return in later feeds or the 19:35 late sweep).
4. **Sentinel blind** (PLT-018): during MAP hours (07:00–19:30 trading days, decision 17) the Worker compares `last_ok_at` with now on each poll attempt; ≥ `sentinel_blind_alert_min` (15) without a successful poll and no open `sentinel_blind` incident → `POST /api/internal/incident` (kind `sentinel_blind`) → S2 opened once + incident email (4.8). The Worker never emails directly and never per tick (NFR-006 DB row).
5. **Kill switch** (DAT-123, AT-21): unchanged token logic (switch off → no request on the next tick); section 9 prints "ASX feed off since <time>" from `worker_state.asx_enabled` / `source_status`.
6. R1 (optional): for alerts on held/watch codes or materiality ≥ 2 the route may call `route('R1', pack)` **after** the P0 emails are sent; output stored in `item_assessment.text_llm` / `alert.text_llm` (in-app only). M5 runs rules-only/mock (decision 21).

### 4.3 Alert delivery (AGT-115, EML-020/022, NFR-012, UX-110, UXN-160/251)
- **P0** (template only): if no P0 email was sent in the last `p0_batch_window_min` (5) minutes → send `p0:<alert_key>` at once inside the ingest request (first P0 immediate); else attach the alert to the open batch (`worker_state.alert_flush_due = window end`) and `alert-flush` sends `p0b:<first key>` listing all P0s of the window when it closes. Duplicates (same key, or same code + same `ann_id` across sources) never email twice. Over the P0 cap or the pool → `suppressed_cap`, listed in section 9. Body (EML-022): what happened (title, code, type), why it matters (tier rule, execution(s) and weight), source link (ASX URL), Melbourne time; no LLM text, no money beyond weight %.
- **P1/P2**: never emailed; written to `alert` for the inbox and listed in section 8. User preference `alert_p1`/`alert_p2` (D-048) `immediate` = counts in the unread badge at once; `digest` = no badge, visible in the inbox and the review. Quiet hours and snooze (UXN-160) hide P1/P2 from the badge only; P0 and the UXN-251 regime P1 are never suppressed. Server API (M7 screens use it): `GET /api/alerts?tier&unacked`, `POST /api/alerts/<key>/ack|snooze` (own rows, all roles, audit `alert.ack`).
