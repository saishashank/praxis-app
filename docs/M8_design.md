### 2.2 Staging pipeline (AT-28, TST-106, NFR-040) — gap found

Inventory finding: the staging Worker dispatches `ref: main` (`worker/src/dispatch.ts`), but every pipeline workflow (`ingest-batch1`, `arena-signals`, `arena-close`, `backup`, `maintenance`, `watchdog`, `replay`, `kb-archive`, `llm-bakeoff`, `backfill-*`) has only a `production` job guarded by `github.ref == 'refs/heads/release'`. A staging dispatch therefore runs nothing; AT-28 cannot pass today.

- **Staging job per workflow** (decision 30): each pipeline workflow gains a `staging` job: `if: github.ref == 'refs/heads/main'`, `environment: { name: staging, deployment: false }` (D-023), checks out the dispatched `main` commit (staging has no approval record; SEC-108 c applies to production only), the same steps as production with staging secrets, and a fixed `PRAXIS_ENV=staging` value. The production job is byte-identical to today (a workflow test diffs it against a stored copy). Secrets stay in `env:` of the steps that need them (SEC-107). `watchdog` and `backup` get staging jobs too (the 20:40 YAML watchdog is a PLT-073 step).
- **Recorded data source** (decision 31): on staging the fetch steps never call Yahoo or ASX (NFR-040). They check out the private fixtures repo read-only with token (f-r) (already in the `staging` environment per SEC-017) and read one recorded AU day (bars, index, announcements, corporate actions) from a fixed layout `recorded/au/<YYYY-MM-DD>/`; a pure, tested mapper re-dates the recorded session to the run's trading date (prices, volumes and texts unchanged). The Worker's real clock drives the run, so the PLT-073 deadlines are real. A host-guard test asserts that no staging step can reach `*.asx.com.au` or Yahoo hosts. Logs print counts and pass/fail only (SEC-110).
- **Deadline checker** (decision 45): `src/lib/runs/deadlines.ts` (pure) reads `run_record`, `completion_marker`, `email_message` and `preopen_run` for one Melbourne date and returns one row per PLT-073 step: step, deadline (from the PLT-073 table held as a code constant, citing `02` l.84), observed start and finish (HH:MM), pass/fail, reason. Early-close days use the same fixed evening times (PLT-073 s13). A CLI `scripts/e2e-day/check.mjs` runs it in the `staging` job of a new dispatch-only `staging-e2e-day.yml` after the 20:45 email window; the job summary shows the table (times and step names only, no data). The same function feeds an Owner-only "Day timeline check" block on System Health.
- **Cold start** (AT-28 s11, decision 3): the second staging day runs on a **fresh empty staging main database** that the Owner creates in Turso and enters into the staging stores (the OPS-040 step 3 procedure, so it doubles as its rehearsal, decision 8). The pipeline needs no special path: migrations run at deploy, the cohort start stage (2.6) opens the cohorts, and every job must reach its marker with "no history" outcomes.

### 2.3 Security baseline (AT-29, TST-107, SEC-010…016, SEC-104, SEC-107)

- **Existing:** static headers (`next.config.ts`, `tests/http/headers.test.ts`), CSP nonce and lock (`src/lib/http/csp.ts`, `tests/http/cspLock.test.ts`), origin gate (`src/lib/http/gate.ts`, `tests/http/gate.test.ts`), rate-limit counter (`tests/http/rateLimit.test.ts`), HMAC (`tests/security/hmac.test.ts`), gitleaks over full history (`ci.yml` job `secrets`), client-bundle secret scan, SEC-109 production 404 (`scripts/smoke/stage2.mjs`).
- **New route-wide tests** (unit, over the generated route list so a new route is covered automatically): every state-changing route refuses a cross-origin or missing-Origin request with 403 and every mutation refuses GET (SEC-011); every rate-limited route class returns 503 when the rate-limit read throws (SEC-014 fail-closed); every JSON write route answers malformed bodies with 400 and never 500 (SEC-013); display-text check over every LLM/third-party text field of the E2E populated seed with adversarial strings (SEC-016).
- **Live-build tests:** an E2E spec requests one route of each class (page, API, public page, 404, auth callback, static asset) from the local production build and asserts HSTS, CSP without `unsafe-inline` in `script-src`, `frame-ancestors 'none'`, nosniff, `Referrer-Policy: same-origin`, `X-Robots-Tag` noindex (SEC-012).
- **ZAP baseline** (decision 7, 37): two runs. (1) In CI on every push: OWASP ZAP baseline (container pinned by digest, Apache-2.0) against the local production build started by the e2e job, unauthenticated plus authenticated with the existing local test login (TST-113 mechanism, never in production builds). (2) Dispatch-only `zap-baseline.yml` on staging (environment `staging`, Viewer session from the test-identity secret (c4)), required by the release gate. Both print only a summary table (rule id, rule name, risk, count; no URL, header value, cookie or evidence) to the job summary; no artifact; the full report is discarded. High findings fail the job; an Owner-approved exception file `scripts/ci/zap-exceptions.json` (rule id, reason, date) is the only way to accept one.
- **Dependency audit** (decision 38): `npm audit --audit-level=high` for the root and `worker/` (production and dev trees reported separately; production high/critical fails, dev high/critical fails unless listed in `scripts/ci/audit-exceptions.json` with reason and expiry ≤ 30 days); `pip-audit` over `scripts/ingest/requirements*.txt` installed with `--require-hashes` from a hashed `requirements-audit.txt` (SEC-107).
- **CodeQL, Dependabot alerts, secret scanning + push protection** (decision 39): GitHub settings the Owner turns on (CodeQL "default setup", no workflow file); the AT-29 report records the setting screenshots' dates, not the values.
- **Workflow lint** (decision 40): a zero-dependency `scripts/ci/workflow-lint.mjs` over `.github/workflows/**`: actions pinned to 40-hex SHAs (container images by digest), no `pull_request_target`, top-level `permissions` no wider than `contents: read`, no `${{ … }}` inside `run:`, `npm ci` only, `pip install` only with `--require-hashes`, no `upload-artifact` except the existing failure-only Playwright report on synthetic data, no `actions/cache` of data paths, every job that reads `secrets.` either runs only on `push`/`workflow_dispatch` or carries the same-repo guard (fork PRs get no secrets, AT-05a). It reads `deploy-*.yml` but nothing in M8 edits them; a finding there is reported to the Owner, not fixed.

### 2.5 Restore drill and the "Restore database" workflow (TST-108, OPS-040, AT-04, AT-30)

- **Decision 4 (option A):** build `.github/workflows/restore-drill.yml`, dispatch-only, environment `production` (`deployment: false`), approved-commit checkout like `backup.yml`, inputs `mode` (`drill` | `restore`), `backup` (release tag of the data repo, default latest), `targets` (`main`, `auth`, `both`). Steps: (1) guard: refuse unless both `BACKUP_PRIVATE_KEY` and `TURSO_PLATFORM_TOKEN_TEMP` are present (step outputs only "present"/"missing"); (2) download the encrypted assets with (f); (3) decrypt in memory with `age-encryption` (already a dependency) — the plaintext never touches the workspace disk beyond a `0600` temp file in `$RUNNER_TEMP` deleted in an `always()` step; (4) create the target database(s) through the Turso Platform API with (l) [VERIFY endpoint names, the "create database" scope and free-tier database count]; (5) restore with the existing `restoreDatabase` (the same code as `scripts/restore/restore.mjs`, which re-reads and compares counts and SHA-256; this is "the real import path" of our format); (6) `drill` only: cohort replay check (below) and delete both databases; `restore` only: keep the new database and print its name only (the Owner creates its tokens in the dashboard, OPS-040 step 3); (7) elapsed time vs the 4 h RTO (NFR-004); (8) **last step fails** while either secret is still present, so GitHub emails the Owner (TST-108). The output is table names, counts, PASS/FAIL and elapsed time only. `scripts/restore/restore.mjs` stays as the local path when GitHub is unavailable (OPS-040 last sentence); its README is updated to remove "none is planned".
- **Build-phase mode:** `mode=drill` with input `key=throwaway` skips the private-key guard, generates a throwaway key pair in the run, asks staging for a fresh backup and auth export encrypted to it (as D-046 does for synthetic data), and restores those into two throwaway Turso databases with a staging-scoped (l). This is the TST-108 build-phase drill that counts for the release gate until AT-30 (TST-112).
- **Cohort replay** (decision 3 note, REQ row 13): production holds no cohorts before go-live (data-only), so the first real-key drill replays a **check cohort**: in the restored throwaway main database it starts one cohort per family seed of E01 at a fixed past start date, runs the DB engine (batch 2a/2b functions) over the restored real bars for a fixed window, and compares every `nav_daily` row with the in-memory replay of D-091 (exact micro-units). From the first quarterly drill after go-live it replays one stored live cohort instead and compares with its stored NAV. Both are deterministic (no clock, SplitMix64 seeds).
- **Nightly watchdog check** (SEC-017 (l)): the production job of `watchdog.yml` gets a step whose `env:` holds `BACKUP_PRIVATE_KEY` and `TURSO_PLATFORM_TOKEN_TEMP` and which fails (step summary "temporary restore secret still present", no value) if either is non-empty. A workflow in the `production` environment can see whether its own secrets are set, so no broader credential is needed; this corrects `scripts/restore/README.md` ("cannot check … not built").

### 2.6 Go-live controls (BLD-030, BLD-024, PLT-071, EML mode)

- **Per-slot runtime switches** (decision 32): `worker/src/schedule.ts` keeps `enabled` as "available in this build"; a new `worker_state` key `slots_enabled` (JSON list of slot names, default absent = today's behaviour) is read in the same single read as `dispatch_enabled` (no extra DB request per tick, TST-124 CPU budget). The M8 release marks every go-live slot available; none runs until the Owner lists it. An Owner-only "Worker slots" block on System Health writes `slots_enabled` (audit-first, confirm dialog), separately for staging and production because each environment has its own database. The master `dispatch_enabled` kill switch stays as it is.
- **`full` mode interlock** (decision 33): `validateMarketModes` accepts `full`; the Owner action in `src/lib/data/controls.ts` refuses `full` in production unless a `go_live_signoff` row exists for the market (new main migration 0012) and `email_mode` is not `off`; staging may switch freely (AT-28 needs it). The sign-off page (`/ops/go-live`, Owner-only) lists each AT-30 item with a tick and date (rotation done + smoke pass date, PAT revoked, real-key drill run id, walkthrough, AT-26 manual check, $0 per provider), shows the release-gate result for the deployed commit computed with token (m) (decision 25), and records the sign-off (audit-first). It never stores a secret, a name or an email.
- **Cohort start stage** (decision 3): no production code calls `startCohorts` today (only tests). A new idempotent stage `ensureCohorts` in batch 2b (`src/lib/arena/cohortStart.ts`), run only when the market mode is `full`, computes the cohort starts due for the next session from the D-076 registry (at go-live: the first cohort of every execution and control, A$600 seed, ARN-001) and calls `startCohorts` (identical starts are skipped). The sign-off evening's normal pipeline therefore creates the cohorts "at M8 exit" and the first trading day runs with no special path; the empty-DB staging day exercises the same code.
- **Email:** `email_mode` stays `off` until sign-off; `incidents` on the sign-off day, `full` the next day after the first 20:00 run (decision 24).

### 2.7 Release gate (TST-112 full gate; decision 25)

- `scripts/ci/release-gate-core.mjs` (pure, with `.d.mts` like `approved-commit-core`) evaluates, for one commit SHA: (1) the PR gate (CI `app`, `secrets`, `worker`, `python` jobs) passed on it; (2) a successful `staging-e2e-day.yml` run on that SHA whose summary marks every PLT-073 row pass (TST-106); (3) a successful `restore-drill.yml` run within 120 days (build-phase mode until a sign-off row exists, real-key mode afterwards; OPS-045 re-approvals exempt); (4) a successful staging `zap-baseline.yml` run on that SHA, with its "authenticated: yes/no" line; (5) a successful `nightly.yml` run on that SHA within 24 h (TST-132). It reads the GitHub Actions API only.
- Used in two places: a `release-gate` job in `ci.yml` on `pull_request` into `release` (`permissions: actions: read, contents: read`, `github.token` only, no secrets), which the Owner adds as a required status check on `release`; and the production sign-off page (via token (m), which already has actions read).

### 2.8 Test-suite completeness (AT-31, TST-120…133)

- **Generated test map** (TST-133): `scripts/ci/test-map.mjs` extracts every requirement ID whose line contains MUST in `spec/01…12` plus the accepted ch.16 P1 IDs, scans test names, test file comments and `docs/test-map.md` rows for cited IDs (BLD-002 makes IDs part of test names), reads the Owner-executed list from ch.14, and writes the CI job summary plus `docs/test-map.generated.md`. CI fails if an ID in `tests/test-map.baseline.json` (IDs covered at the last run) loses its last test. AT-31 needs zero uncovered IDs; the report lists the gaps for the tasks to close.
- **Diff coverage** (TST-120, decision 20): `scripts/ci/diff-coverage.mjs` (zero-dependency) joins `git diff -U0 <base>` with lcov from vitest (`src/**`), the Worker vitest run (`worker/src/**`) and `node --test --experimental-test-coverage --test-reporter=lcov` for `scripts/**/*.mjs`; fails below 90 % lines or 80 % branches on changed lines. Base: the PR base, or `github.event.before` on push (so the long-lived `build` branch is measured per push). Self-tested on fixture diffs and fixture lcov.
- **Coverage floors** (TST-121, decision 12): a CI `coverage` job runs `test:coverage` with 80 % overall lines and 90 % on the named groups (§5 decision 12).
- **Mutation** (TST-130, decision 22): StrykerJS with the vitest runner over the money and statistics modules; weekly `mutation.yml` (schedule + dispatch, no secrets, summary only); score ≥ 80 %.
- **Nightly full suite** (TST-132): `nightly.yml` (schedule + dispatch; staging environment; only if `main` moved since the last green run, or when dispatched): E2E against staging with the test identity, TST-127 visual comparison with the fixtures baselines via (f-r), email template tests, job tests, Worker tests; ≤ 25 min.
- **Flaky tests** (TST-131, decision 13): `tests/quarantine.json` (test id, date, reason, due ≤ 2 days to fix or quarantine); a check fails on any `.skip`/`.only`/`test.fixme` without a matching entry; Playwright's retry results are listed in the summary as "flaky".
- **Workflow re-enable** (PLT-015, TST-112a; gap: neither exists): the production Worker checks once a day, with token (b), the state of the scheduled workflows (`nightly`, `mutation`, and any YAML backup trigger) and re-enables any that GitHub disabled for inactivity, raising an in-app notice each time; a Worker test simulates the 60-day disabled state.
