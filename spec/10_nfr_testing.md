## 10.1 Reliability and recovery
- **NFR-001** Nightly pipeline completion marker by 19:45 Melbourne on ≥ 95% of AU trading days in any 30-day window.
- **NFR-002 (s9)** Sentinel: ≥ 98% of **scheduled polls per source** succeed during announcement hours while the Worker is running (ASX every 4 min per DAT-122; other sources per their cadence); Worker outages are detected by PLT-074 (Vercel Cron 00:xx UTC = 10:00–10:59 AEST / 11:00–11:59 AEDT and 11:xx UTC = 21:00–21:59 AEST / 22:00–22:59 AEDT).
- **NFR-006 (s9) Incident channels** (single table; supersedes other wording):

| Event | Channel |
|---|---|
| Missing completion marker at 19:50 | in-app incident only; the "partial" review is the email |
| No review email sent by 20:40 | YAML watchdog calls the email route; if that fails (Vercel down or paused) it sends a **minimal review directly through the Resend API** (key is a `production` environment secret) from the last completion data; fallback timing is best-effort (scheduled runs may start late) and outside NFR-003 |
| Worker last poll stale (checked by both Vercel Cron heartbeats **and** the 20:40/21:50 watchdog) / review missing at heartbeat | incident email via Resend **and** the watchdog/heartbeat workflow run **fails on purpose**, so GitHub's own "workflow failed" email reaches the Owner independently of Resend — the deliberate failure happens when an incident **opens**, and afterwards at most once a day (21:50) while it stays unacknowledged |
| Database unreachable (Turso down) | de-duplication state is unavailable, so only the heartbeat and watchdog runs alert: at most one "database unreachable" email per run, and the watchdog run fails; the Worker never emails per tick |
| Unapproved production code (SEC-108 d) | S1 incident email + watchdog deliberate failure; GitHub's deployment-review emails and Vercel's production-deployment emails (enabled at M0 [VERIFY on Hobby]) are independent signals; runbook OPS-045 |
| Market in production data-only mode (BLD-024) | heartbeat and watchdog skip email/review checks for that market; data-pipeline and Worker checks still apply |
| Sentinel blind (running Worker, source failing) > 15 min | incident email |
| Quota ≥ 90%, backup failure, invariant violation, degrade mode, 401/403 from a provider | **one** incident email when the incident opens (and one when it escalates to S1), then only review section 9 until closed |

- **NFR-003** Evening Review delivered 20:00–20:45 Melbourne on ≥ 28 of any 30 days once a recipient is configured (§1.6 of Ch. 01).
- **NFR-004 Recovery objectives:** RPO ≤ 24 h (nightly backup, PLT-022); RTO ≤ 4 h for the database via the documented restore; ≤ 1 h for app/worker redeploy.
- **NFR-005 Graceful degradation:** any provider outage leads to degrade mode (PLT-051), never to data corruption; every skipped step is visible in System Health and the review.

## 10.2 Performance
- **NFR-010** Dashboard FCP < 2 s (mobile, 4G), Lighthouse performance ≥ 80; API p95 < 500 ms for page data.
- **NFR-011** Nightly deterministic compute for all executions, controls and challengers ≤ 10 minutes of Actions time per market; learning loop ≤ 5 further minutes (ARN-100); weekly light replay ≤ 30 minutes and monthly full replay ≤ 90 minutes (ARN-100); total within PLT-014.
- **NFR-012 (s9)** P0 alert latency (item published → **first** P0 email sent) ≤ 5 minutes median for non-ASX sources and ≤ 9 minutes median for ASX items (4-minute poll).

## 10.3 Data integrity and reproducibility
- **NFR-020** Ledger invariants ARN-101 run nightly; a violation stops new entries for that execution and raises an incident.
- **NFR-021** Every write that changes positions/cash is transactional (order, fill, position, cash ledger, cohort state together).
- **NFR-022** Re-running a cohort with the same inputs, versions and seed reproduces identical trades and NAV (ARN-102).
- **NFR-023** Append-only tables: fills, cash ledger, change ledger, audit events, decision cards, lessons. Corrections are new rows referencing the corrected row. Audit rows carry a hash chain — each row stores the HMAC of the previous row's content; the nightly watchdog verifies the chain and alerts on a break **(s11)**.

## 10.4 Security
### 10.4.1 Identity and roles (O-22; supersedes PLT-030 "single owner email")
- **ROL-101a (s9) Auth isolation.** The user, allowlist, session_version and audit tables live in a **separate auth database** whose token only the production (and, separately, staging) Vercel app holds; the Owner's email is also pinned in a Vercel environment variable and the Owner role is granted only when it matches. An optional **break-glass recovery email** (`OWNER_RECOVERY_EMAIL`, a Google address distinct from the primary Owner account) may be stored, disabled by default and enabled only by a documented procedure; every use is alerted to the Owner and audit-logged **(s11)**. Workers and Actions never hold the auth-DB token. The auth DB is backed up nightly by a **signed Vercel route** that exports it already **encrypted to the backup public key**; the backup job fetches only that ciphertext (DAT-143, PLT-022b); the **production** export route always uses the configured public key (k) and rejects any caller-supplied key — only the staging route accepts an in-run drill key (TST-108); OPS-040 and TST-108 include restoring it. The production auth DB is shared across all active markets; no per-market allowlist isolation **(s11)**.
- **ROL-101** Google OAuth sign-in for an **allowlist** of verified Google emails, each with a role: **Owner** (exactly one: the Owner's address), **Editor**, **Viewer**. New entries default to Viewer. Role and allowlist status are read from the database on **every** request.
- **ROL-102** Owner only: allowlist and roles, secrets status, configuration, market activation, source switches, corporate-action review, rule edits, challenger approval/force-apply/rollback, kill switches. Editor: annotate, acknowledge alerts, run what-if replays within a daily budget (5 per user per calendar day, Melbourne timezone, resets 00:00 **(s11)**), personal settings. Viewer: read-only. Editors MUST NOT change rules or configuration.
- **ROL-102a (s9) Role × action matrix** (server-enforced; anything not listed is Owner-only):

| Action | Owner | Editor | Viewer |
|---|---|---|---|
| Read all pages except Usage/Admin/Ops/logs | ✓ | ✓ | ✓ (codes masked per ROL-107) |
| Own user_preference; own alert acknowledgement | ✓ | ✓ | ✓ |
| Annotations on lessons/cards/hypotheses | ✓ | ✓ | — |
| What-if on pre-computed tables (UX-119), ≤ 5/day per user (reset 00:00 Melbourne **(s11)**) | ✓ | ✓ | — |
| Unmask codes for non-owners (ROL-107) | ✓ | — | — |
| Users, markets, sources, config, data review queue, rules, challengers, kill switches, secrets status, Usage, Ops, logs | ✓ | — | — |

- **ROL-102b (s11) Annotations.** Editors and the Owner may annotate lessons, decision cards and hypotheses with plain-text notes (≤ 1,000 characters); annotations are created inline on the respective pages. Visibility: visible to all users (no role masking). Author or Owner may edit or delete an annotation. Every annotation create/edit/delete is audit-logged.

- **ROL-103** Nothing in v1 places or records real trades for anyone.
- **ROL-104** Every sign-in (success/failure), role change, allowlist change and Owner action writes an append-only audit event; revocation takes effect on the next request. **Revocation is confirmed by a modal dialog; the revoked user is NOT emailed **(s11)**.**
- **ROL-105** Email in v1 goes to the **Owner only** (the Resend test sender can only deliver to the account's own address — EML-003a).
- **ROL-107 (s9) Sharing safeguards.** Before the first non-Owner is added, the Owner records in Settings → Users & roles an acknowledgement via a **checkbox control** **(s11)**: "I have checked, or accept, the risk that sharing code-level signals may be regulated financial advice (AFSL) and that some sources are licensed for personal use only" (stored as an Owner decision); the Add-user button stays disabled until then. This acknowledgement is **re-recorded (rechecked) when a new market activates** **(s11)**. Non-Owners see code-level signals and Decision Cards **masked by default**; masking hides the code, company name, trade prices, trade-level dates (weeks only), evidence source links and any code/company name inside LLM text (UX-009); the Owner can unmask per user (audit-logged, 30-day expiry). DAT-124 applies. **(s13)** The acknowledgement is an audit-logged Owner decision row in the auth DB (who, when, text version).
- **ROL-106** Every page visible to non-owners carries "Simulation for personal information only — not financial advice"; before adding users outside the family the Owner SHOULD check whether sharing outputs requires an AFSL (PRD-025) [VERIFY with a licensed professional]. Other users' emails are never sent to an LLM (LLM-036).

### 10.4.2 Sessions and web security
- **SEC-010 (s9)** Sign-in via a maintained library (e.g. Auth.js) with PKCE and state; require `email_verified = true`; bind each allowlist entry to the Google `sub` at first sign-in and refuse later mismatches. Sessions: HttpOnly, Secure, SameSite=Lax cookies; lifetime ≤ 14 days; each request re-validates role and a per-user `session_version` (incremented by sign-out-everywhere or revocation).
- **SEC-011** State-changing requests require same-origin (Origin/Referer check) plus SameSite cookies; no state change via GET.
- **SEC-012** Headers: HSTS, Content-Security-Policy without `unsafe-inline` scripts (nonces allowed), `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`; `robots` noindex (PLT-036).
- **SEC-013** All inputs validated against schemas server-side; parameterised queries only; output encoding by the framework; no rendering of third-party HTML.
- **SEC-014** Rate limits stored in the database (serverless-safe): sign-in callback ≤ 10/min per IP; write endpoints ≤ 60/min per user; exports ≤ 5/hour per user. If the rate-limit DB lookup fails, the request MUST be rejected (HTTP 503) rather than allowed through **(s11)**. **(s13)** Read endpoints (company search, lists, quotes) ≤ 60 requests/min per user; quote refresh is served only from the shared cache (UXN-048).
- **SEC-015** Machine-to-machine calls use per-caller secrets with constant-time comparison (PLT-032).
- **SEC-016 (s9) Safe links and markup; text shown to people.** LLM output is rendered as plain text; every stored/rendered URL must be `https:` with a host in the source register (DAT-120), else shown as non-clickable text; email HTML comes only from templates with escaped fields. Every LLM text **and every third-party headline or title** shown to a person (emails, alerts, cards, summaries, lessons) passes a deterministic **display-text check** (no model call): URLs, domains, email addresses, and credential/account-action phrases aimed at the reader ("sign in", "verify your account", "rotate/enter your key", "password", "your token", "API token"); ordinary market imperatives ("sell-off deepens") are allowed. Text that fails is replaced by the rules-only text (for titles: "[title withheld — see source]"). KB-032's classifier stays for playbook text only. Every email and the Settings page carry the fixed footer: "Emails from this system never ask for keys or passwords. Sign in and do rotations only via your own bookmark." The review's app link opens a view-only page (apart from "Mark as read").
- **SEC-017 (s9) Separate machine credentials** (signed calls: HMAC-SHA256 over body + timestamp, rejected if older than 300 s or replayed, POST only — except Vercel Cron routes, which are GET by platform design and are authenticated with the `CRON_SECRET` bearer token, idempotent and local-date guarded). **Secret → stores table** (the rotation page and OPS-040 use this table): **(s13)** `PII_HASH_KEY` (NFR-030) is a production secret held only in Vercel/GitHub production stores and is in the OPS-045 rotation list; rotation does not re-hash old rows.

### 10.4.3 Secrets and supply chain
- **SEC-101** Secrets are never pasted into chat, email, markdown or tickets. The Owner enters each secret directly into GitHub **environment** secrets, Vercel environment variables or Cloudflare Worker secrets. The build agent supplies only the list of names and a **CI credential smoke test** that proves each secret works without printing it (DB round-trip on a temp table, one test email to the Owner per manual run with subject "[TEST]", Worker dry-run deploy, OAuth config check); it is run manually, not on every push. Secrets that Actions cannot see are proven by a **signed self-check route on Vercel** and, for the cron-only Worker, by a **self-check on a cron tick** after each deploy and daily; each reports pass/fail per secret it holds (never the value) to a run record shown on System Health.
- **SEC-102 (s10, O-30)** The build agent works through a separate GitHub **bot (machine) account** owned and controlled by the Owner (GitHub allows one machine account per person), added to the code repo as a collaborator with the **Write** role, two-step verification on, and a classic token per SEC-017 (a), expiry ≤ 90 days. The bot is never a reviewer of any environment, never an admin, and has no access to the data or fixtures repos. Secrets are entered only by the Owner (SEC-101). At go-live the bot is removed as a collaborator (or its token revoked) and re-added only for later build sessions.
- **SEC-103** Secrets are never stored in any database table.
- **SEC-104 (s10)** $0 security tooling only: GitHub **secret scanning + push protection** on the public code repo (free for public repos), **gitleaks** (or trufflehog) in CI and as a pre-commit hook on both repos (the private data repo has no free GitHub secret scanning), Dependabot alerts, CodeQL (free for public repos), `npm audit` / `pip-audit`, OWASP ZAP baseline before each release. No paid pen tests or paid storage.
- **SEC-105** Real auth tests: Owner signs in; a non-allowlisted Google account is refused server-side; a revoked user is refused on the next request; an expired session is refused.
- **SEC-106** Roles are defined by ROL-101…106.
- **SEC-021 (s9) Rotation policy.** Max ages per the SEC-017 table: expiring tokens on schedule (reminders at 14/7/2 days); non-expiring keys yearly and immediately on suspicion; **every production secret in SEC-017 rows (b)–(j) and (m), in all stores, plus the staging dispatch token (b-s) and staging Resend key, once at go-live** (SEC-108 c, AT-30); (a) is revoked and (k) never touched GitHub during the build. One guided rotation page lists, for each secret, every store to update and the exact screens, then runs the smoke test. **(s13)** Expiry reminders at 30/14/7/2 days; System Health lists every secret expiring in the next 60 days so the Owner can rotate before a planned absence.
- **SEC-020 (s9)** The Owner MUST enable 2-step verification on the Google, GitHub, Vercel, Cloudflare, Turso, Resend, Google Cloud and LLM-provider accounts (M0 checklist).
- **SEC-108 (s10, O-29) Trust model with a public code repository.** The code repo is **public** (the data repo stays private). On GitHub Free a public repo provides branch protection, **environments with their own secrets, deployment-branch policies and required reviewers**, and free secret scanning — so: (a) **No repository-level secrets.** Every secret lives in a GitHub **environment**: `production` (deployment branch: `release` only), `staging` (`main` only), `ci-fixtures` (holds only the read-only **fixtures-repo** token; deployment-branch rules allow this repo's branches and `refs/pull/*/merge`, and every job using it also requires that the pull request's head repository is this repository — fork runs never receive environment secrets), `deploy-production` (branch `release`, **required reviewer = the Owner**; holds the Cloudflare and Vercel deploy tokens) and `deploy-staging` (`main`). Jobs on any other branch, and every fork pull request, receive no secrets. (b) **Branch protection** on `main` and `release`: pull request required, **1 approving review required** (only the Owner can give it — the bot authors the PRs and GitHub does not let authors approve their own), **"Require approval of the most recent reviewable push"**, required status checks (PR gate), no force-push, no deletion, and **"Do not allow bypassing the above settings"**; `release` is updated only by merging a PR from a branch pinned at the chosen commit (`rc/<sha>`). (c) **Production deploys and production code need the Owner's approval in GitHub:** Vercel production and the production Worker are deployed only by jobs in `deploy-production` (Vercel's own git auto-deploy for production is off), which wait until the Owner approves them in GitHub ("Review deployments", with an email notification). The bot account (O-30, SEC-102) is a Write collaborator only, so it cannot change protections or environments, approve its own pull requests or approve a deployment. **Every `production` workflow checks out the commit of the latest approved `deploy-production` deployment** (read via the GitHub API), not the `release` head, so a merged release runs nothing new until the Owner approves it; merging and approving are done in one sitting (M0 row 18), and a release left unapproved for > 3 days shows an in-app notice. (d) **Residual and detection:** with the bot account every change to `main` and `release` needs the Owner's review, so unapproved code cannot reach production secrets; the bot can still push to its own feature branches and run workflows there, but those jobs get no environment secrets (a). As defence in depth, a nightly check in the production Vercel app reads GitHub with token (m) and raises an **S1** incident if the deployed Vercel commit (`APP_COMMIT`, passed in by the deploy job [VERIFY whether `VERCEL_GIT_COMMIT_SHA` is set for CLI deploys]), the production Worker's reported build commit, or the commit recorded by any production run differs from the latest **approved** `deploy-production` deployment (runbook OPS-045); until a first approved deployment exists it shows "awaiting first approval". **As a fallback if GitHub is unreachable or token (m) is compromised, a DB-stored signed record of the last approved deployment commit is checked; this secondary record is written by a separate, signed Vercel route at approval time and verified by the nightly check as a hash match **(s11)**. (e) At go-live (M8) the Owner rotates every production secret and removes the bot collaborator (or revokes its token); later build sessions re-add it with a new short-lived token. (f) The backup **private** key is never stored on GitHub (PLT-022b). (g) Vercel **Standard Deployment Protection** is on and Git fork protection stays on. Releases are batched to at most one per week.
- **SEC-110 (s10, O-29) Public-repository rules.** Everything in the code repo, its workflow files, **workflow run logs**, commit history, pull requests and signed-in-downloadable artifacts is public. Therefore: (a) the code repo contains **no** market data, announcements, fundamentals, recorded provider responses, decision cards, ledgers, lessons, playbooks, backups, decision logs, session logs or personal data (names, email addresses) — data, knowledge and backups live in the private data repo; **test fixtures** recorded from ASX/Yahoo live in a separate private **fixtures repo** (`<repo>-fixtures`) fetched at test time with the read-only token (f-r); the Owner's `docs/`, `log/` and `RESUME.md` never enter the code repo; a CI check blocks data-like files (CSV/Parquet/JSON above a size, PDF, HTML captures) outside an allowlist of synthetic fixtures, and any email address or the Owner's name; (b) **logs, run names, `workflow_dispatch` inputs and job summaries** (all public) contain only counts, ids, timings and pass/fail — never secret values, email addresses, prices, codes of positions or signals, or third-party text; tests that use real-data fixtures run with quiet reporters (test id + pass/fail only; no expected-vs-actual diffs) and write full reports to the private data repo; (c) no Actions **artifacts or caches** contain data (reports with data go to the data repo); (d) fork pull requests: "require approval for all external contributors" to run workflows, no `pull_request_target`, no environment jobs on `pull_request` from forks; Issues, Discussions, Wiki and Projects are disabled on the code repo; (e) commits use the Owner's GitHub **noreply** email; the Owner's email and other personal data are only in environment variables; **application and workflow code MUST NOT log/echo/print any environment secret; secret values are registered with the GitHub Actions masker **(s11)**; (f) **no licence is granted** (no LICENSE file; the README says the repo is public only to use free CI, all rights reserved) [PROPOSED]; (g) the strategy rules and prompts are visible to anyone — accepted by the Owner (O-29); (h) GitHub **secret scanning and push protection** are enabled (free for public repos) in addition to gitleaks.
- **SEC-109 (s9) Test identity guard.** The staging-only test login (TST-113) also has a runtime guard (refuses when the environment is production or the project id is the production project), uses its own signing secret, and a production smoke test asserts it returns 404.
- **SEC-107 (s9) CI hardening:** third-party Actions pinned to full commit SHAs; `pull_request_target` forbidden; untrusted inputs never interpolated into `run:`; workflow `permissions:` default `contents: read`; any change to `.github/workflows/**` or secret names is listed in the build digest under "Security-relevant changes"; Dependabot auto-merge off; lockfiles with hashes (`npm ci`, `pip --require-hashes`); each job receives only the secrets it needs. **PR gate includes a check that every workflow in `.github/workflows/**` uses `pip install --require-hashes` (never bare `pip install` or `npm install`; `npm ci` only) **(s11)**. Rotation per SEC-021.

## 10.6 Strategy validation addenda (extend Ch. 05 §5.10)
- **VAL-101 (s9) No uncalibrated forward-looking probabilities.** Any model-predicted probability or "confidence %" MUST come from a model with a stored calibration report on held-out data. Empirical frequencies (ARN-070–072) with n and CIs and the PRD-020 table labelled "illustrative model" are allowed. **(s13)** A calibration report is a stored record {model id + version, held-out window, n, reliability bins, Brier score, created}; a probability without a linked report MUST display 'not yet calibrated' (checked by AT-27).
- **VAL-102 (s9) Multiple testing and evidence timeline.** DSR and PBO are computed and used exactly as in VAL-110 (ARN-087), with the trial count of ARN-085. Each execution shows an evidence timeline: forward signal-ledger trades and effective-N cohorts so far, the expected date to reach 100 forward trades and ≥ 5 effective cohorts at the measured signal rate, each family's earliest possible validation date computed from ARN-082 (e.g. F5's snapshot requirement), and which label (ARN-086) is reachable when; for slow families this may be several years and is stated plainly.
- **VAL-103 "Accuracy" is not a gate.** Any gate phrased as "X% accuracy" (e.g. market pivots) is replaced by: the relevant families hold CONSISTENT-FORWARD (ARN-086), beat control C2 per ARN-081 after VAL-102 correction, and show no kill-switch event (ARN-093) in the last 60 sessions.
- **VAL-104 No CAGR gates.** Backtest "CAGR ≥ x%" gates and "beat Lane A by > y%" tests are void; promotion/retirement follow ARN-065/081/092 and KB-041.
- **VAL-105 First-30-day success** = Ch. 01 §1.6 system metrics + Ch. 14 acceptance tests passing + evidence timeline populated. Return targets over 30 days are not success criteria.

## 10.7 Test strategy
- **TST-100 Unit tests** for simulator, cost profiles, sleeve, indicators, rule interpreter, quality checks, time handling: ≥ 90% line coverage on these modules; ≥ 70% overall [PROPOSED]. **(s13)** Overall and critical-module floors are superseded by TST-121.
- **TST-101 Known-answer tests.** Hand-computed cases MUST pass exactly: P5 brokerage at each tier boundary (A$1,000.00 / 1,000.01 / 3,000.00 / 3,000.01 / 10,000.00 / 10,000.01 / 25,000.00 / 25,000.01); marketable-parcel rejection; deployable-cash rule (ARN-024a); tick-based slippage; exit types IS/CS and the stop-fill formula (ARN-021); initial stop set from the actual fill; dividend receivable from ex-date; non-renounceable offer; suspension haircut and legacy ledger (ARN-026); twin restart and shadow continuation (ARN-053); **stalled** terminal state at the stall floor for 5 sessions (same floor U and L) and via 20 sessions of parcel-only rejections; liquidation-NAV terminal checks; C2 exit mapping in ATR units for F2/F3/F6 (ARN-004); sleeve margin counted once in NAV (ARN-041/051); P2 rule; T+2 settlement; stop hit inside range; gap through stop fills at open; worse-case ordering when an IS stop and a CS/trailing trigger both occur in one bar; sleeve close-out at 50% margin; loss capped at margin; REC-2 unlock; split and consolidation without artificial P/L; dividend credited on pay date; franking recorded separately; minimum order and participation cap; whole-share rounding. **(s13)** Every case MUST be stored in the private fixtures repo with inputs and exact expected outputs, including one case on each side of every P5 tier boundary and one parcel-rejection case.
- **TST-102 Golden dataset.** A frozen dataset (≈ 20 codes × 3 years per market incl. a split, a consolidation, a delisting, a halt, a rights issue) reproduces identical trades/NAV on every run and every platform.
- **TST-103 Time tests.** Melbourne DST start (first Sunday in October) and end (first Sunday in April), plus US DST changes, for every scheduled job and the 20:00 email; exchange holidays; early closes.
- **TST-104 Property tests** for ledger invariants (ARN-101) under random order sequences.
- **TST-105 Integration** with recorded provider responses (no live calls in CI): full pipeline data → signals → orders → fills → review.
- **TST-106 Staging E2E day:** one full simulated trading day on staging (separate Turso DB, test providers, email to the Owner only) completes by the deadlines of PLT-073.
- **TST-107 Security tests:** SEC-105 cases; CSRF/origin checks; headers present; ZAP baseline with no high findings; secret-scan clean history.
- **TST-108 (s9) Restore test:** quarterly after go-live, restore the latest encrypted main-DB and auth-DB backups into **two throwaway Turso databases** (main and auth; created with the temporary token (l), not connected to any app — this exercises the real import path), verify checksums of forever tables, replay one cohort to identical NAV, then delete both databases and revoke (l). The private key is added only for the drill and removed afterwards; the workflow's last step fails (so GitHub emails the Owner) while the private-key secret or (l) is still present, and the nightly watchdog repeats that check. Any active build-agent PAT is revoked before a real-key drill and a new short-lived PAT is issued afterwards if the build continues. **During the build (M1–M7)** — at M1 exit and whenever backup or restore code changes — the drill job **generates a fresh throwaway key pair inside the run**, requests a fresh staging backup and staging auth export encrypted to that public key within the same run, restores them into two throwaway Turso databases (main and auth; created with (l)) and verifies checksums — so the real private key never meets an active PAT and no throwaway key is stored anywhere; cohort replay is added once cohorts exist (M3). The real key is checked without GitHub: at M0 the Owner performs the guide's offline encrypt/decrypt test with the real key pair, and each monthly offsite download includes a local decrypt-only check. The first real-key drill is part of M8 after the PAT is revoked (AT-30).
- **TST-109 No-look-ahead test:** perturb all data after date D; decisions for D and earlier MUST be unchanged.
- **TST-110 Coverage-matrix sync:** every data family in DAT-150 appears in AGT-130's matrix or is marked "stored, not used".
- **TST-111 LLM bake-off** per LLM-040…042 before role assignment and monthly.
- **TST-112a (s11) Workflow re-enable test.** A test exercising the 60-day inactivity disable/re-enable path for batch workflows (PLT-015): simulate 60 days of inactivity, assert the workflow is re-enabled automatically, and verify the in-app notice appears.
- **TST-114 (s10) CI minutes.** The code repo is public, so standard-runner minutes are free (O-29); CI still keeps a self-imposed soft budget of ≤ 600 minutes/month for speed and fair use, with path filters, dependency caching (no data in caches, SEC-110) and combined PRs; one-off heavy work (history backfill into files, DAT-101 evaluation, AT-17 null runs) may run on Actions or in the build agent's own environment; tests that need recorded real-data fixtures run in the `ci-fixtures` environment (SEC-110), fork PRs run only synthetic tests. **(s13)** Soft budget raised to 1,000/month by TST-132.
- **TST-115 (s9) Where tests run** — the **single source** for test environments (Ch. 12 and Ch. 14 refer here). **Staging (recorded data):** TST-100…107, 109, 110, 112; AT-02, AT-03 (history and bundle scans), AT-04, AT-05a, AT-07, AT-08, AT-09 part A (perturbation), AT-10…AT-17, AT-18 part B, AT-19, AT-20 (except the inbox check and the watchdog fallback), AT-22…AT-29, TST-108 build-phase drills, TST-111 bake-off, AT-M2, AT-M3, AT-M5. **Production** (data-only mode from M2, BLD-024; for IN/US from their build start): AT-03 (smoke test stages 1–2), AT-05 (except its inbox check), AT-05b, AT-20 watchdog fallback (one forced run in M5 with the review check enabled), TST-108 real-key drills, AT-06, AT-09 part B (daily snapshots stored), AT-18 part A, AT-21, AT-M1, AT-M4. **Owner-executed:** AT-01, the inbox checks of AT-05 and AT-20, AT-30, AT-M0. Workflows can be dispatched only if their file exists on the default branch (`release`), so new staging/test workflows reach `release` through an approved release before they can run.
- **TST-112 (s9) Gates.** PR gate: TST-100–105, TST-107 static/header checks, TST-109, TST-110 (unit + recorded integration; path filters and dependency caching). **Infrastructure release gate (M1–M7):** PR gate + the CI smoke test + ZAP baseline + the exit tests of completed milestones; it allows production deploys for the data-only mode (BLD-024). **Full release gate (from M8):** PR gate + TST-106 on staging + a TST-108 pass within 120 days (the OPS-020 reminder fires at day 75; re-approving a known-good commit under OPS-045 is exempt; build-phase staging drills count until AT-30, real-key drills afterwards; a release uses the last AT-04/TST-108 pass within 120 days — drills are not re-run per release) + ZAP baseline (authenticated with a staging Viewer session, or the report states authenticated pages were not scanned).
- **TST-113 (s9) Test identities.** The Owner provides three Google test accounts (Editor, Viewer, non-allowlisted) for the manual AT-01 run; automated E2E on staging uses a staging-only signed test-identity login that is compiled out of production builds.

### 10.7a Complete test suite — "no change untested" (O-40, s13) [OWNER]
- **TST-120 Change rule.** Every pull request that changes behaviour MUST add or update tests for that behaviour. CI MUST fail when **changed lines** have < 90% line coverage and < 80% branch coverage (`diff_coverage_min`, `diff_branch_min`), measured on unit + integration tests together. Pure docs/config-text changes are exempt only when CI detects no executable change.
- **TST-121 Test layers.** The suite MUST contain all of: **unit** (pure logic), **integration** (module + DB/HTTP with recorded responses, TST-105), **contract** (every boundary below), **end-to-end** (UI in a real browser), **job** tests and **scheduled-time** tests (TST-103). Overall coverage floors (`coverage_overall_min` 80% lines; 90% on money maths, validation statistics, rule interpreter, auth/roles, Worker scheduling) replace the 70% overall in TST-100.
- **TST-122 Services / API.** Every API route and server action MUST have tests for: success, validation errors, auth required, **each role (Owner/Editor/Viewer/none) allowed vs refused**, masking (ROL-107), rate limits (SEC-014), CSRF/origin (SEC-011) and error shape. A generated route list MUST match the tested-route list (CI fails if a route has no tests).
- **TST-123 Jobs.** Every scheduled or dispatched job (nightly batches, backfill, backups, reminder email, quota meter, watchdogs) MUST have tests for: normal run on the golden dataset; **idempotent re-run** after a crash at each stage; missing predecessor marker (DAT-020 s13); provider off / quota exhausted (degrade paths, PLT-051); DST/holiday dates. Job-to-job ordering is tested end to end in TST-106.
- **TST-124 Worker (Sentinel).** Cloudflare Worker logic MUST run in the local Workers runtime in CI: slot schedule, ≤ 720 ASX requests/day, CPU budget per tick (assert below the free limit with margin), signed calls to Vercel, dispatch of batch 2, lock/duplicate protection.
- **TST-125 Contracts.** Each boundary has a schema-checked contract test on both sides: Worker → Vercel route (HMAC), Actions → Vercel (HMAC), app → Turso schema (migration tests up and down on a copy), app → Resend payload, LLM router → provider request/response shape, data provider parsers on recorded samples. A schema change without a matching contract update fails CI.
- **TST-126 UI end-to-end.** Playwright (free) on a production build against the staging test identity (TST-113): every page and tab, both roles' views, empty / stale / error states (UX-007), the six themes (UXN-280) at desktop and phone width, keyboard navigation, and the "Simulated" label audit (AT-27). **Accessibility:** automated axe checks with no serious/critical issues on every page.
- **TST-127 Visual regression.** Screenshot comparison of every page × {Dark, Light} × {desktop, phone} and the two email templates; baselines stored in the **private fixtures repo** (never the public repo); a change above the pixel threshold fails until a reviewed baseline update is committed.
- **TST-128 Component tests** for shared UI components (tables, charts, Decision Card, region switcher, Control Room ring) with representative props, including long text and zero/negative/missing values.
- **TST-129 Email tests.** Evening Review, 8am reminder and alerts render from fixtures; size ≤ limits (EML-013), plain-text part present, no remote images, links correct, partial-review box (EML-011), snapshot-compared.
- **TST-130 Mutation testing** on money maths and validation statistics: weekly mutation run; surviving-mutant score ≥ 80% (`mutation_score_min`); results summarised, not gating each PR.
- **TST-131 Flaky tests.** A test that fails and then passes on retry is flagged; flaky tests are fixed or quarantined within 2 days with an issue; quarantined tests still run nightly and are listed in System Health. No test may be deleted or skipped to make CI pass (AGENT_PLAN §6).
- **TST-132 Where and when.** PR gate: affected unit, integration, contract, API and component tests + diff-coverage check (path filters keep it fast). Nightly on staging (only on days with merged changes): full suite incl. E2E, visual, email and job tests. Weekly: mutation tests. Release gate: full suite green within the last 24 h. Budgets: PR gate ≤ 10 min, nightly full suite ≤ 25 min; `ci_minutes_budget` raised to soft 1,000/month (public repo, standard runners are free — O-29); re-measured at M4.
- **TST-133 Test map.** The repo keeps a generated **test map** (requirement ID → tests) published in the CI summary; every MUST in ch. 01–12 and every accepted ch. 16 P1 item has at least one test or is listed as Owner-executed in ch. 14. CI fails if a MUST loses its last test.

## Acceptance criteria — Chapter 10
- **Given** a Viewer session, **when** it calls any write endpoint, **then** it gets 403 and an audit event is recorded (ROL-101/104).
- **Given** a revoked Editor with a valid cookie, **then** the next request is refused (ROL-104).
- **Given** the CI smoke test, **then** each secret is proven to work and no secret value appears in logs (SEC-101).
- **Given** the TST-101 cases, **then** all pass exactly.
- **Given** data after D is perturbed, **then** decisions up to D are identical (TST-109).
- **Given** the quarterly restore test, **then** checksums of forever tables match (TST-108).
- **Given** a displayed probability, **then** a stored calibration report backs it (VAL-101).
- **Given** 30 days in production, **then** NFR-001…003 are met or each miss is explained by a logged incident.
