# Chapter 04 — Email & Notifications (Resend): the 8 pm Evening Review  (v2.0, session 10)

_Changes from v0.1 (session 5): the daily email is now the **Evening Review at 20:00 Australia/Melbourne** with the owner-specified content (trades, profit/loss, what was learned, tomorrow's improvements, overall success %). The 08:00 Morning Brief is now optional and off by default. The recipient is the Owner's Gmail address (O-20), stored as configuration (`OWNER_EMAIL`)._

## 4.1 Provider and constraints
- **EML-001** Email MUST be sent through the owner's **free Resend account** [OWNER]. The API key is a secret (PLT-040).
- **EML-002** Resend free plan limits (V, Resend docs): **100 emails/day, 3,000/month, 3 custom domains, 10 requests/second (shared), 30-day data retention; received and sent emails both count; bounce rate must stay < 4% and spam rate < 0.08%.**
- **EML-003** The owner does **not** want DNS/domain work, so v1 uses **no custom domain**. The sender is therefore Resend's shared test sender, which (to be verified at build) can deliver only to the **email address that owns the Resend account** [VERIFY at build]. The recipient MUST therefore equal the Resend account email. The address is the Owner's Gmail address (O-20); EML-006 remains only as a guard for a missing configuration value.
- **EML-004** Self-imposed budget: ≤ 20 emails/day and ≤ 300/month; two daily slots are reserved for the Evening Review and new S1/S2 incidents; emails suppressed by the cap are listed in section 9 (NFR-006). Staging uses its own Resend key and prefixes every subject with "[STAGING]"; staging sends ≤ 1 inbox email per test run. **(s13)** One further daily slot is reserved for the EML-023 attention reminder.
- **EML-005** The recipient address is held in a Vercel/Actions **environment variable** (`OWNER_EMAIL`, set at M0), never hard-coded, never sent to any LLM, and never written to logs beyond the delivery record; with the Resend test sender it MUST equal the Resend account email. Settings shows it read-only (UX-115).
- **EML-003a** _(s8)_ Recipient supplied: the Owner's Gmail address (O-20; value only in `OWNER_EMAIL` and the private docs). Resend's `resend.dev` test sender only delivers to the Resend account's own address (V, Resend docs), so the Resend account MUST be registered to that address.
- **EML-003b** _(s9)_ All emails go to the **Owner only** (ROL-105); Editors/Viewers read reviews in-app.
- **EML-012a** _(s9)_ With more than one active market, the review contains one block of sections 1–8 per active market (AU first), followed by shared sections 9–10.
- **EML-006** **Until a recipient address is configured**, the system MUST NOT fail: it renders and stores each Evening Review in-app (Digest history), shows a "set recipient address" banner on the dashboard, and starts emailing automatically once the address is set (optionally including a catch-up of the last 3 reviews' headlines).

## 4.2 Daily Evening Review (primary email)
- **EML-010** The system MUST send **one Evening Review per local calendar day at 20:00 Australia/Melbourne** (target window 20:00–20:45), every day including weekends and public holidays (on non-trading days the trading sections are replaced by research/learning and weekend-preparation content). Sending is idempotent per local date.
- **EML-011** **Sequencing:** the review is assembled from the *completed* nightly pipeline (end-of-day data, marking to market, trade reviews, lesson extraction — Chapter 05 §5.8). The pipeline MUST finish by ~19:30–19:45 (ASX announcements platform closes 19:30 (V)). If it has not finished by 20:30, the review is sent (by 20:45) marked **"partial"** listing what is missing; a completed version is not re-sent but is stored in-app. **(s13)** A partial review starts with a box 'Partial review — not ready by 20:30:' listing the missing section numbers and names.
- **EML-012** **Content**, in this order (summary first, then detail):
  1. **Headline scorecard** — day's total simulated P/L per active currency **(s11)** across the 12 executions, best and worst execution, executions that reached a terminal state today (target / bust / stalled / timeout) with a link to the execution detail page **(s11)**, system health. No FX-converted grand total is shown **(s11, O-34)**.
  2. **Investments made today** — per execution: each buy/sell with price, size, costs, stop/target, the reason (signal) and link to the Decision Card **(s11, UX-041)**; plus positions carried overnight. When empty: "No paper orders today" **(s11)**.
  3. **Profit / loss** — per execution: day P/L, current NAV, distance to the target, cohort P/L, realised vs unrealised, costs paid, **leverage-sleeve P/L and lock status** (locked/unlocked and recovery progress).
  4. **What was learned today (and fed to the agents)** — new observations and lessons with grades and evidence counts; which agent knowledge notes changed (Lane A); **rule/parameter changes only when a challenger was promoted** (before → after, VAL-110 result), otherwise the status of challengers and, if promotion is currently impossible, why and when it could first become possible; observations *not* applied and why.
  5. **What worked better and why** — comparison across the 12 executions: strategy family, universe tier (core / mid / small), signal, market regime, costs, leverage on/off; and what didn't work and why.
  6. **What needs improving for tomorrow** — the next-day plan: adjustments queued, watchlist/candidates, known events tomorrow (results, ex-dividend, RBA/ABS), risk flags, data or agent weaknesses found.
  7. **Overall picture — success %** — investment success (win rate, expectancy, average win/loss, profit factor), **each agent's signal success %** (Chapter 05 §5.9: ARN-073/074/075; agents without a defined signal test show "n/a") **(s11, QNT-R2-01)**, execution success as CIFs of target, bust and stalled with n and effective N (cumulative, never short rolling windows), versus the matched controls and the zero-edge benchmark, with validation labels and minimum detectable effect; short windows (7/30 days) are shown only for trade counts with intervals.
  8. **Sentinel recap** — significant announcements/alerts of the day and how they affected positions.
  9. **System & quota health** — job freshness, data freshness, LLM budget/fallbacks, free-tier usage percentages, last backup.
  10. **Footer** — "Simulation for personal information only; not financial advice", app link.
- **EML-013 (s9)** Format: responsive HTML plus plain-text alternative; **≤ 90 KB** (Gmail clips above ≈ 102 KB); per-execution detail collapsed to one line each with a link to the in-app review; the top screen MUST be a self-contained summary; no remote images or tracking pixels; tables and simple text glyph bars for visuals; links to authenticated app pages (no sensitive data in URLs). **(s13)** Size = bytes of the complete HTML part before transfer encoding (Gmail clips at about 102 KB of HTML); AT-20 measures it this way.
- **EML-014** The review body MUST be generated **deterministically from stored data**. An LLM (role R5) MAY write the narrative parts (sections 4–6) from structured facts within the token budget, but the email MUST still send with template text if no LLM is available. When no LLM is available, sections 4–6 are replaced by a facts-only bullet list headed "Written without AI today" **(s11, UXP-R1-08, OPS-R1-06, BLD-R1-15)**, listing lessons, rule changes and next-day plan from stored fields. All numbers come from data, never from the LLM (LLM-034).
- **EML-015** Every review MUST be stored in the app (Digest history) as markdown/HTML and also as a dated markdown document in the knowledge base (Chapter 08), forming the running learning journal.
- **EML-016** Settings MUST allow: pausing the Evening Review; enabling an optional **Morning Brief at 08:00** (default off; content: overnight news, today's calendar, tonight's plan) **sent only on trading days of the active market** **(s11, UXP-R1-18)**; changing the send time. **(s13)** 'Active market' = a market whose MKT-106 status is `active`.

## 4.3 Alert emails
- **EML-020** **Critical (P0) alerts** MAY trigger an immediate email capped at **10 per day**; bursts within 5 minutes MUST be batched; duplicates suppressed.
- **EML-021** **System incident emails** follow the NFR-006 table (one email when an incident opens or escalates; combined token-due emails). A single LLM provider falling back, or rules-only mode caused by a provider's daily quota (PLT-051), is reported in section 9 only and never emails.
- **EML-022** Alert emails state what happened, why it matters, the source link and the time in Australia/Melbourne.
- **EML-023 [OWNER] (s13) Daily "needs attention" reminder.** Every day (weekends and holidays included) at `attention_reminder_time` (default 08:00 Melbourne) the system MUST re-check the Control Room (PLT-061, UXN-283) and, **only if at least one component is amber (needs attention) or red (down)**, send the Owner one reminder email; when everything is healthy no email is sent. Subject: "Praxis: <n> item(s) need attention — <first item> (day <d>)". Body, per open item: component, what is wrong in one plain sentence, open since (date and day count), deadline if any (e.g. token expiry date), the one-line fix and a link to that item in the Control Room (and to the OPS-037 checklist where relevant); then a short "Resolved since yesterday" list. Content comes from stored health facts through a fixed template (never LLM-written, LLM-034); no money figures; HTML + plain text ≤ 20 KB. At most one reminder per day; it counts toward EML-004 and uses one reserved slot. It does not replace immediate P0/S1 alerts (EML-020, NFR-006). The Owner MAY snooze an amber item for 1, 3 or 7 days (≤ `attention_snooze_max_days`) from the Control Room; red items and items within 2 days of a hard deadline cannot be snoozed. Reminder on/off and time are Owner-only settings (default on). If Resend is unavailable, open items still show in the Evening Review section 1 and as an in-app banner.

## 4.4 Reliability
- **EML-030** Sending retries up to 3 times with backoff; every attempt is recorded (time, status, provider message id).
- **EML-031** If delivery fails, the dashboard shows a banner and the review remains readable in-app.
- **EML-032** Jobs MUST tolerate GitHub Actions start delays of 5–30 minutes; "on time" means sent between 20:00 and 20:45 local.
- **EML-033** Time handling MUST be correct across daylight-saving changes (PLT-019).
- **EML-034** A "send test email" action MUST exist (rate-limited).
- **EML-035 (s9)** The email job MUST verify the completion marker for that date (trading or `non-trading`, DAT-022) before sending (EML-011) and MUST NOT include yesterday's data as today's; IN/US blocks follow the review-date rule of DAT-010.
- **EML-036 (s9) Inbox delivery.** M0 includes a Gmail filter so the Resend test sender never goes to spam (BLD-010). "Delivered" = accepted by Resend; the email links to the in-app review, where a **"Mark as read" button (POST)** records reading; a review is also marked read when the email link is clicked **(s11, UXP-R1-13)**; if no review is marked read for 3 days the Dashboard shows a banner.
- **EML-037 (s9)** Section 7 always shows P(target) together with P(bust) and P(stalled), versus matched controls (ARN-071); sections 4–5 describe differences only when ARN-062's test passes, otherwise "no detectable difference (n = …)"; single-day best/worst are labelled "single-day result — noise".

## Acceptance criteria — Chapter 04
- **Given** an ordinary trading day with the recipient configured, **when** 20:45 Melbourne time has passed, **then** exactly one Evening Review for that date exists in delivery records, in Digest history and in the knowledge base.
- **Given** the nightly pipeline finished, **then** the review contains all ten sections, including per-execution trades and P/L, lessons with evidence counts, before→after parameter changes, tomorrow's plan, and success % by agent and by execution.
- **Given** the pipeline is late, **then** a "partial" review is sent by 20:45 and the complete one is stored in-app.
- **Given** no recipient address is configured, **then** nothing fails, reviews accumulate in-app, and a banner explains what to set.
- **Given** all LLM providers are unavailable, **then** the review is still sent with template text and full numbers.
- **Given** the workflow runs twice for the same date, **then** only one email is sent.
- **Given** 12 P0 events in an hour, **then** alert emails respect the daily cap and bursts are batched.

- **(s13)** **Given** the Turso token expires in 12 days (Security amber), **when** 08:00 Melbourne arrives, **then** exactly one reminder email is sent naming Security, the expiry date and the fix link; **given** all components healthy, **then** no reminder is sent; **given** the item is snoozed for 3 days, **then** no reminder for it is sent on those days; **given** a red item, **then** snooze is not offered (EML-023).
