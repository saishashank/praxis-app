# Chapter 11 — Operations Runbook  (v2.0, session 10)

_Replaces the imported draft v0.1. Requirements only — no code; commands are named, not scripted. Times are Australia/Melbourne; all cron expressions are generated from configuration (OPS-102), never typed by hand._

## 11.1 Operating model
- **OPS-001** The system is designed to run unattended. The Owner's routine is **reading the 20:00 Evening Review (≈ 3 minutes/day)**. **Realistic total Owner time budget:** ≈ 3 min/day (+ ≈ 1 min per P0/P1 alert on days they occur **(s11)**) + ≈ 30 min/week (queue, challengers, and ≈ 5 min per release approval — releases are batched to at most one per week) + ≈ 45 min/month (licence re-check, $0 check, offsite download) + ≈ 1–2 h/quarter (restore drill, rotations due) + a one-off ≈ 1 day at M0 and ≈ 2 h at go-live (token rotation, sign-off). Tasks that need a technical helper (offline restore without GitHub) are marked as such; everything else is surfaced there or in System Health. There is no on-call rota; response times below are targets for a single person.
- **OPS-002** Canonical schedule: PLT-073 (Ch. 02). Every job writes a run record; System Health flags any job older than 2× its interval (PLT-017).

## 11.2 Automated daily checks (no human action unless flagged)
- **OPS-010** Checked every night and reported in Evening Review section 9: job freshness; Sentinel coverage (NFR-002); data-quality verdict per market (DAT-210); corporate-action queue length; ledger invariants (NFR-020); quota percentages (PLT-050); LLM fallbacks/budget; last backup; source switches off; open incidents.
- **OPS-011** Incident emails (EML-021) follow the NFR-006 table (one email when an incident opens or escalates; token warnings at 14/7/2 days): Sentinel blind > 15 min in announcement hours; a critical job failing twice; data-quality gate failing two consecutive nights; quota ≥ 90%; backup failure; ledger invariant violation; degrade mode entered; heartbeat misses (PLT-074: 00:xx UTC = 10:00–10:59 AEST / 11:00–11:59 AEDT and 11:xx UTC = 21:00–21:59 AEST / 22:00–22:59 AEDT).

## 11.5 Runbooks (symptom → checks → actions)
- **OPS-030 Nightly job did not run / email missing.** Check System Health run records → GitHub Actions run list → Worker dispatch log (PLT-071) → token expiry (PLT-074). Jobs are idempotent per (job, market, local date) (PLT-076), so re-dispatching is safe. Actions: manually dispatch the workflow from the GitHub UI; if the Worker is down, redeploy it (OPS-050); the email job sends "partial" automatically if the pipeline is late (EML-011). **If stages 1–9 ran successfully but only the completion marker write failed, re-dispatch is sufficient (stages are idempotent); the marker is written by the re-run **(s11)**. **OPS-030a: Critical batch failure in the trading window (Batch 2, fills/decisions) during a Turso outage.** If Turso recovers within 4 hours after a critical-batch failure (same night), the Owner may manually re-dispatch that batch from the GitHub UI; the completion marker is written by the re-run. If recovery takes longer than the trading window of the next calendar day, that day is skipped for trading and flagged as an incident in Settings **(s11)**.**
- **OPS-031 Sentinel blind.** Check Worker logs and last successful poll per source → licence register switches → provider status. Actions: redeploy Worker; if one source is failing/blocked, switch it off (DAT-123) so others continue.
- **OPS-032 Data-quality gate failed (DAT-210).** Open System Health → quality details per tier → cross-source disagreements and missing codes. Actions: if the primary source is down, confirm fallback use; if data is wrong for specific codes, leave them blocked (entries resume automatically when checks pass); if systematic, switch the source off and record in the decision log.
- **OPS-033 Corporate-action queue item.** Open Settings → Data review; compare the evidence (announcement link, price jump) → confirm/edit/reject. Affected codes unblock after reprocessing (DAT-222).
- **OPS-034 Quota ≥ 90%.** Open Usage → identify the consumer (market/job). Actions: degrade mode reduces non-essential work automatically (PLT-051); consider pausing a market in `testing` or `in build` (MKT-104/106); never add a payment method (PRD-007).
- **OPS-035 LLM budget exhausted / provider down.** No action needed (rules-only fallback, LLM-050); review the bake-off if persistent.
- **OPS-036 Source objection or block (e.g. ASX).** Switch the source off immediately (DAT-123); record the event and any correspondence in the licence register; the Sentinel continues on other sources. Resume only with written permission.
- **OPS-037 Suspected secret leak.** Revoke/rotate the secret at the provider → update the secret store → run the CI smoke test → review audit events and provider logs → record an incident. **A pre-written emergency-rotation checklist and optional GitHub `workflow_dispatch` template exists per secret in SEC-017 for faster execution under incident pressure **(s11)**.** **(s13)** The build agent MUST deliver the per-secret emergency-rotation checklist (revoke → replace in every SEC-017 store → smoke test → record) as a private M0 document; AT-M0 checks it exists for every SEC-017 row.
- **OPS-037a (s11) Suspected backup-key compromise.** If the offline backup private key (`age` pair) is suspected compromised: generate a new key pair offline → add the new public key to GitHub environment `production` and production Vercel env → backup existing databases with the new public key → revoke the old public key from all stores → rotate the old private key's storage location. Schedule a full restore drill once the new key is verified.
- **OPS-038 Unauthorised access in audit log.** Revoke the user (Settings → Users) → sign-out everywhere → rotate session secret → review audit events.
- **OPS-039 Wrong trade / suspicious P/L.** Open the trade's Decision Card and fills → check corporate actions and bar validity for those dates → if data was wrong: correct via the review queue; the simulator reprocesses from the event date (DAT-222, NFR-023); record a lesson if systemic.

## 11.6 Backup, restore, deploy, rollback
- **OPS-040 (s9) Restore database.** Target RTO ≤ 4 h **counted from when the Owner starts** the procedure (NFR-004). Steps (Owner guide has screenshots): (0) revoke any active build-agent PAT; (1) add the **offline private backup key** and a **temporary Turso platform token** (the narrowest scope that can create a database, shortest expiry offered [VERIFY scope/expiry options]) as secrets of the GitHub `production` environment; (2) run the **"Restore database"** workflow (inputs: backup id, target = main DB and/or auth DB) which decrypts the backup, creates a new Turso DB by whole-database import and verifies checksums (TST-108); (3) in the Turso dashboard create the new database's tokens, one per SEC-017 caller, and enter each — **together with the new database URL** — directly into every store listed for it in the SEC-017 table (never through a workflow log); then redeploy the current production Vercel deployment (same commit, so it passes the approval check) and the Worker (OPS-050) so both pick them up (main DB: Vercel env, Actions, Worker; auth DB: Vercel env only); (4) delete the temporary token and the private-key secret (the workflow fails until they are gone); (5) run the smoke test and record the incident. If GitHub itself is unavailable, the restore from the monthly offsite copy needs a technical helper or the build agent, working from a local machine with the same steps. **OPS-040a (s11) Owner account recovery.** If the Owner loses access to the primary Google account (O-33): (1) attempt Google's own account-recovery process (2-step verification + backup codes); if unsuccessful, (2) enable the `OWNER_RECOVERY_EMAIL` environment variable (a pre-registered Google address) as an allowlist entry in the auth database (Vercel production env); (3) sign in with the recovery email and change the allowlist so the recovery email becomes the primary Owner email (or revert after regaining access to the primary account); (4) immediately disable `OWNER_RECOVERY_EMAIL` and record the recovery event in Settings.** **(s13)** Owner decision O-38 (Q-065): all accounts keep 'Sign in with Google'. Accepted residual risk: if the Owner's Google account is locked, recovery of Vercel/GitHub/Cloudflare/Turso depends on recovering Google via O-33 (2-step verification + offline backup codes); the M0 checklist MUST record that the backup codes are stored offline and tested once. [OWNER]
- **OPS-041 (s10) Deploy.** All changes by pull request; the PR gate and release gate of TST-112 apply. A merge to `main` deploys **only staging** (staging Vercel project + staging Worker, `deploy-staging`). Production: when the release gate passes, the build agent (or the guide's web step) opens a PR from a branch pinned at the chosen commit (`rc/<sha>`) into `release`; the Owner merges it; the `deploy-production` job then **waits for the Owner's approval in GitHub** ("Review deployments", GitHub emails the Owner) and deploys Vercel production and the production Worker (SEC-108 c). A nightly check raises an S1 incident if the `release` head or a deployed production commit differs from the latest approved deployment (SEC-108 d). Knowledge archives and backups go to the separate private data repository (PLT-022a) and never trigger a deployment.
- **OPS-042 Roll back a deployment.** Redeploy the previous successful deployment (Vercel "promote previous", Worker previous version) and revert the commit.
- **OPS-043 Roll back a rule version.** Knowledge → family → version history → rollback (KB-043); effective at the next cohort boundary.
- **OPS-044 (s9) Vercel paused or down for long.** Symptoms: UI unreachable; review arrives as the watchdog's minimal version. Checks: Vercel dashboard usage/pause notice. Actions: identify the consumer from the Usage history in the last minimal reviews; reduce the load (degrade mode, fewer replays); wait for the pause to lift or redeploy; never add a payment method (PRD-007). Actions batches keep the data and ledgers current meanwhile.
- **OPS-045 (s9) Unapproved production release (S1).** Symptoms: S1 email / watchdog failure / Vercel deployment email you did not expect. Actions: roll back production (OPS-042) to the last approved commit; revoke the build-agent PAT; rotate **all** production secrets the unapproved code could read — the `production` and `deploy-production` environment secrets, every production Vercel-env secret (c1–c3, d, e, h, i, j, m), the production Worker secrets (the unapproved code ran with `production` secrets and could have used them against the Worker), the staging dispatch token (b-s — it can dispatch any workflow) and the staging Resend key (it can email the Owner from the whitelisted sender); bump every user's `session_version` (signs everyone out); reject any pending production deployment and re-deploy the known-good commit with an explicit approval; compare Settings → Users with the expected allowlist; run the ledger invariants (ARN-101) and, if the allowlist, audit trail or ledgers look altered, restore from a pre-incident backup (OPS-040); review the commits on `release`; record the incident; resume only after approving a known-good release. The AT-05b test push is pre-registered as an expected test incident and does not trigger this runbook.
- **OPS-050 Redeploy the Worker.** Trigger the Worker deploy workflow by `workflow_dispatch` on ref `release` (its first-step ref guard still applies); confirm the next minute's run record.

## 11.8 Build-phase reporting
- **OPS-101 Build digest.** During the build, a GitHub Action emails the Owner (≤ 1/day, 20:00 Melbourne) a digest generated from commits, CI results, open blockers listed in the private `docs/06_open_questions.md` (GitHub Issues are disabled, SEC-110 d) and milestone status (Ch. 12). It contains only measured facts; no hand-written progress percentages.
- **OPS-102 Generated schedules.** Cron expressions and UTC conversions are generated from the configured local times and market calendars, with the dual-trigger + local-time guard of PLT-019; the runbook never lists hand-typed UTC times.

## Acceptance criteria — Chapter 11
- **Given** the YAML schedule does not fire, **then** the Worker dispatch runs the job and no human action is needed (OPS-030, PLT-071).
- **Given** a source is switched off, **then** within one cycle no request reaches it and the next review says so (OPS-036).
- **Given** the restore procedure into a throwaway database, **then** it completes within 4 h of starting with matching checksums for the main and auth DBs (OPS-040).
- **Given** a merge to `main`, **then** only staging (app and Worker) deploys and a failing test blocks it; **given** a new `release` head without an approved deployment, **then** nothing deploys to production and an S1 incident is raised that night (OPS-041).
- **Given** the build phase, **then** the Owner receives at most one digest per day containing only generated facts (OPS-101).
